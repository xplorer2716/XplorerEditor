# RQ-SET — Settings Service

Scope: C++ replacement of `AllUsersSettingsService` / `AllUsersSettings`.

- **RQ-SET-001** — The application shall persist settings shared by all users of the machine in a per-machine application-data location (reference: `ProgramData\Xplorer\Xplorer`), surviving application restarts.
  - *Amended 2026-08-19 (owner report, session SET, ADR-SET-001 DEC-SET-001):* **On Linux and macOS, "per-machine" is qualified to "per-machine when writable, else per-user."** The reference per-machine location (`commonApplicationDataDirectory`, which JUCE maps to `/opt` on Linux and `/Library` on macOS) is root-owned, and this project ships no installer on either platform to grant a standard user write access there (confirmed: `linux-x64`'s AppImage and the macOS `.app` are both unpacked/copied, never installed by a privileged step — ADR-BLD-004). Writing there therefore always failed silently, which is the reported defect: settings never persisted, and every restart re-derived from an unrelated, effectively-undefined in-memory state instead of the documented defaults (see ADR-SET-001 for the second, compounding defect this exposed). The service now falls back to the platform's per-user application-data directory (`~/.config/Xplorer/Xplorer` on Linux, `~/Library/Xplorer/Xplorer` on macOS) whenever the per-machine one cannot be created. Windows is unchanged and unaffected — `%ProgramData%` already accepts a standard user's write, which is why the defect never showed there.
- **RQ-SET-002** — The settings shall include the MIDI configuration: synth input device name, synth output device name, automation input device name, SysEx transmit delay, MIDI channel, editing program number, synth type (Xpander/Matrix-12), smart-all-notes-off flag, and the CC automation table.
- **RQ-SET-003** — The settings shall include the UI configuration (knob LED/border color, knob movement linearity) and the randomizer configuration of the reference.
  - *Amended 2026-08-06 (owner report, session GUI, ADR-JUC-009 DEC-JUC-106):* **"knob style" is dropped from this list.** It persisted `knobStyleIsStandard`, but no rendering code ever read it (confirmed by reading every consumer before removing it) — the field, the Settings-dialog "Knob style" radio pair, and its XML element are all removed; see RQ-GUI-031's amendment for the full rationale. A pre-existing settings file (including one imported from the .NET reference, RQ-SET-006) that still has a `KnobStyleIsStandard` element loads unchanged — the element is simply no longer read, the same tolerance RQ-SET-007 already relies on for optional entries.
- **RQ-SET-004** — When the settings file is missing or unreadable, the service shall fall back to documented defaults and continue; a reset-to-defaults operation shall be provided.
- **RQ-SET-005** — The settings service shall be injectable behind an interface (no global static access from the controller), enabling unit tests with in-memory settings.
- **RQ-SET-007** — The UI configuration SHALL additionally persist a **per-block colour override** for the eight functional blocks of the block-identity palette (VCO, LAG, TRACK, VCF, ENV, LFO, RAMP, MODULATION MATRIX — RQ-DSN-092), stored in the same per-machine settings file and in the same 32-bit ARGB form already used for the knob LED/border colour (RQ-SET-003). Each entry SHALL be **individually optional**: an absent or unset entry means "use the design-system default", so a settings file written before this feature — including one imported from the reference .NET version (RQ-SET-006) — loads without error and yields the default palette. A reset-to-defaults operation SHALL clear the overrides rather than write the current defaults as explicit values, so a later change to the design-system palette is picked up by users who never customised their colours. **Dependencies:** RQ-SET-001, RQ-SET-003, RQ-SET-004, RQ-SET-006; RQ-DSN-092, RQ-DSN-095.
  - **Acceptance (Gherkin):** *Given* a settings file with no block-colour entries, *When* the application starts, *Then* every block uses its design-system default and no error is raised. *Given* the user sets an override for two blocks, *When* the application is restarted, *Then* those two blocks use the stored colours and the other six use the defaults. *Given* overrides exist, *When* reset-to-defaults runs, *Then* the entries are removed from the settings file (not rewritten with literal default values).

- **RQ-SET-006** — When a settings file produced by the reference .NET version is present, the service shall import its values (one-way migration) or, failing that, start with defaults without crashing.
