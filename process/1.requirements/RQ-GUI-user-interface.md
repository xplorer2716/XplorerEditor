# RQ-GUI — User Interface (JUCE)

Scope: JUCE reimplementation of the WinForms View layer (MainForm, dialogs, MidiApp.UIControls).
Inputs: reference screenshot + owner's textual description (2026-07), `MainForm.Designer.cs` (4487 lines, 234 custom controls), `MainForm.resx` (background bitmap + button icons).
Owner decisions (2026-07): reuse the existing background bitmap; **resizable** main window; functional parity with standard JUCE controls first, custom skin afterwards.

## Main window — global structure

- **RQ-GUI-001** — The main window shall present all single-patch parameters simultaneously on one screen, laid out over the reference background image (block diagram of the synth signal path), organized as: LEFT column = VCO1, VCO2, FM/VCA, LAG, TRACK X blocks; CENTER column = MULTIMODE VCF/VCA1/VCA2, ENV X, LFO X, RAMP X blocks; RIGHT column = VFD display, shortcut buttons, modulation matrix.
  - *Defect closed 2026-08-18 (owner report, session GUI): the VCF/VCA block's second VCA rendered as "VCA" instead of "VCA2" — this requirement's own wording already had the same typo, next to a model that has always named the pair `VCA1_VOL`/`VCA2_VOL` (`XpanderConstants.hpp`). Corrected here and in both renderers (`generate_background_mockup.py`, `BackgroundRenderer.cpp`).*
- **RQ-GUI-002** — The UI shall bind every control to its model parameter by name through a registration mechanism (control identifier → parameter name), so control changes call `SetParameter` and controller events update controls, with no per-control hand-written glue.
- **RQ-GUI-003** — When a parameter-change event arrives from the controller (automation or synth), the affected control shall update without echoing the change back to the synth.
- **RQ-GUI-004** — While a control is being edited from the UI, its mapped CC automation shall be temporarily disabled (RQ-FMW-033).
- **RQ-GUI-005** — The main window shall be freely **resizable**: the whole content (background bitmap and controls, positioned on a fixed logical canvas) scales uniformly with the window, preserving aspect ratio (owner decision; supersedes the reference's fixed launch-time DPI sizing).
- **RQ-GUI-006** — The UI shall run on the JUCE message thread; controller events arriving from other threads shall be marshalled to it (RQ-FMW-061) via the `EventDispatcher` seam.
- **RQ-GUI-007** — The main window shall use the reference background bitmap extracted from `MainForm.resx`, rendered scaled; a vector redraw is a post-parity evolution (ADR-JUC-006).
- **RQ-GUI-008** *(corrected 2026-08-04, session GFX — owner report: menu order, icons and shortcuts do not match the reference; the parenthetical menu list below was an approximation made at parity time, before `MainForm.Designer.cs`/`.resx` were read item-by-item and cross-checked. It is superseded by the verified structure in this amendment, architecture ADR-JUC-032.)* — The main window shall provide the reference menu bar, in the reference's own order, labels, icons and keyboard shortcuts — extracted and verified directly from `MainForm.Designer.cs`/`MainForm.resx` (`XplorerEditor-dotnet-archive`), not approximated:
  - **File**: New (`Ctrl+N`, icon), Open (`Ctrl+O`, icon), *separator*, Save (`Ctrl+S`, icon), *separator*, Exit. **Deviation (owner-confirmed 2026-08-04):** the reference's `Save as` (`Ctrl+Shift+S`) is dropped — the JUCE "Save" already always prompts for a destination file (no tracked current-file path exists or is planned), making a separate "Save as" redundant with it. Recorded here as the deviation rule requires, not left as a silent omission.
  - **Patch**: Previous (`F5`), Next (`F6`), Go to patch... (`F7`), *separator*, Randomize (`F8`), Rename (`F9`), Store (`F10`), Synchronize (`F12`).
  - **Tools**: Settings (`Ctrl+G`), Tune Request (`F4`), Single patches...▸[Get all single patches from synth, Extract all single patches from file], Backup/Restore...▸[Backup all data, Restore all data].
  - **Help**: Xplorer help (`F1`), *separator*, Check for new releases, Go to website, About....
  - **View** (owner-added, RQ-SCL-002/RQ-SCL-003, no reference equivalent) and **Piano keyboard** (Tools submenu item, RQ-GUI-028, no reference equivalent) are the only two sanctioned departures from the reference — every other menu, submenu, order, label, icon and shortcut SHALL match it exactly. Piano keyboard keeps its current position (after Tune Request) and carries no shortcut, since the reference has none to match.
  - **Icons.** The reference has exactly **three** menu icons in the whole application — New, Open, Save (File menu only) — no other item, in any menu, has one. They SHALL be reused verbatim from the reference's embedded bitmaps (`MainForm.resx`, base64 `System.Drawing.Bitmap` resources), not redrawn, following the precedent of the shortcut buttons' hover/down GIFs (RQ-GUI-007) and the About dialog's image (RQ-GUI-025) — both already reuse original reference bitmaps rather than a vector reinterpretation.
  - **Shortcuts are both displayed and functional.** Every reference `ShortcutKeys` value above SHALL both appear as the item's shortcut text in the dropdown and actually trigger that item's action when pressed, matching the reference's own dual behaviour (`ToolStripMenuItem.ShortcutKeys` does both in WinForms). No item outside this list carries a shortcut — in particular Exit, Save (dropped above), Save/Rename/Store/Goto's own dialogs, and About have none in the reference, and SHALL have none here either.
  - **New loads the bundled default patch, not a blank one.** The reference's "New" calls `FileOperationsManager.NewPatch()`, which loads `oberheim.syx` (shipped beside the executable) through the same single-tone load path as Open — there is no blank/reset state. The JUCE "New" SHALL do the same: load the repository's `oberheim.syx` through the existing tone-load path, using whatever program number the file's own sysex data specifies (verified: the reference sets no program number itself — it comes from the file).
  - **Synchronize, Xplorer help, Check for new releases and Go to website are real actions, not placeholders.** Synchronize re-fetches the current patch from the synth (`sendProgramChangeAndGetSinglePatchFromSynth`, already implemented, used by Goto/Store today) — no new controller work. The three Help items open a URL in the system browser: the user manual, the GitHub releases page, and the project website, respectively (same URLs as `XplorerConstants` in the reference).
  - plus, beyond the .NET reference, a **View** menu (scale presets 1x/1.25x/1.5x/1.75x/2x, Full Screen) added by RQ-SCL-002/RQ-SCL-003 for window-size/scale management, placed between **Patch** and **Tools** in the bar order.
  - **Acceptance (Gherkin):** *Given* the menu bar, *When* each menu is opened, *Then* File/Patch/Tools/Help show exactly the items above, in that order, with that wording. *Given* the File menu, *When* it is opened, *Then* New/Open/Save show their reference icon and no other item in any menu shows one. *Given* the application has focus, *When* any shortcut above is pressed, *Then* the corresponding action fires and the same text is visible next to its menu item. *Given* an item with no shortcut in the reference, *When* the menu is read, *Then* it shows none. *Given* "New" is invoked, *When* it completes, *Then* the tone loaded matches `oberheim.syx` and the program number is whatever that file specifies. *Given* "Synchronize", *When* invoked, *Then* the current patch is re-fetched from the synth exactly as Goto/Store already do. *Given* "Xplorer help" / "Check for new releases" / "Go to website", *When* each is invoked, *Then* the corresponding URL opens in the system's default browser. *Given* the View menu and the Piano keyboard item, *When* the menu bar is read, *Then* they are the only two items with no reference counterpart.
  - **Dependencies:** RQ-GUI-007, RQ-GUI-025, RQ-GUI-027, RQ-GUI-028, RQ-SCL-002, RQ-SCL-003; ADR-JUC-032.

## Page families (shared control blocks)

- **RQ-GUI-010** — The ENV X, LFO X, RAMP X and TRACK X areas shall each be a **single shared control block** whose controls edit the currently selected family instance; selector buttons (ENV 1–5, LFO 1–5, RAMP 1–4, TRACK 1–3) switch the active instance.
- **RQ-GUI-011** — When a selector button is clicked, the block's controls shall rebind to the selected instance's parameters (name = family prefix + digit, per `PageFamilyDescriptor`), refresh their displayed values from the model, and the controller shall send the matching page-select to the synth (reference `TriggerRuleManager`/`PageRefreshManager` behavior). Each selector button shall carry the reference caption — `ENV 1`…`ENV 5`, `LFO 1`…`LFO 5`, `RAMP 1`…`RAMP 4`, `TRACK 1`…`TRACK 3` (the `.Text` from `MainForm.resx`), not the bare instance digit.
- **RQ-GUI-012** — When the synth selects an ENV/LFO/RAMP/TRACK page (page-change event, RQ-CTL-023), the corresponding selector shall activate and the block shall refresh, mirroring the synth panel.

## Modulation matrix panel

- **RQ-GUI-015** — The matrix panel shall present the 20 modulation entries as 4 groups of 5 rows; each row = source combo box, amount knob (−63..+63), destination combo box, quantize checkbox (reference tags `MOD_SOURCE_n`, `MOD_AMNT_SRC_n`, `MOD_DEST_n`, `MOD_QUANTIZE_n`).
- **RQ-GUI-016** — Row edits shall call the controller matrix operations (RQ-CTL-030); destination combos shall only offer destinations allowed by the max-6-sources rule, and source editability shall follow `sourceAvailabilityForEntry`.
- **RQ-GUI-017** — Modulation-entry-change and full-tone-change events shall refresh the affected row(s)/whole matrix without echoing to the synth.
- **RQ-GUI-018** — The matrix shall highlight rows related to the control under the mouse, as the reference (`InitializeModSourceHighlight`): hovering a page-family selector that is a modulation source (ENV/LFO/RAMP/TRACK n) shall highlight every source combo currently set to that source; hovering a knob that is a modulation destination shall highlight every destination combo currently set to that destination **and** whose row has an active source (≠ NONE). The highlight clears on mouse-leave. Paged knobs (ENV/LFO) resolve their destination against the currently selected family instance.
  - *Amended 2026-08-03 (owner decision, session GUI) — the **rendering** of the highlight is superseded by RQ-GUI-052; the **trigger and row-selection rules above are unchanged**.* The original statement highlighted by repainting the combo's **background** with the knob LED-border colour. Both clauses are withdrawn: RQ-GUI-052 gives the combo's background a permanent meaning (the functional-block identity of its selected value), so repainting it on hover would erase that information for exactly as long as the user is looking at it, and the LED accent would sit on top of a block-coloured control it has no relation to. The highlight becomes a **frame** treatment instead (RQ-GUI-052), leaving the background untouched. *Rationale for keeping this requirement rather than merging it into RQ-GUI-052:* the cross-reference logic — which rows match, the ≠ NONE filter, the paged-instance resolution — is behaviour, is already implemented and headless-tested (`ModulationHighlight`), and is unaffected by how the result is drawn. **Dependencies:** RQ-GUI-052, RQ-CTL-030; ADR-JUC-010, ADR-JUC-028.

## VFD display & shortcut buttons

- **RQ-GUI-020** — The UI shall show a display area at top-right presenting at minimum: current program number and patch name, and the last edited parameter on change. The parameter line shall follow the reference `VfdDisplayHelper` content: the parameter's end-user display name (Resources.resx string, tag as fallback) and its value formatted by control type — combo/radio selection **label**, checkbox `Y`/`N`, knob numeric — plus the mapped `MIDI CC:` number when one exists — the reference's unassigned-CC sentinel (last entry of the CC name list, value 128) shall never be shown as if it were a real CC *(fixed TASK-JUC-089, issue #11)*; a modulation-matrix edit shall instead show `SRC TO DEST:` with `AMNT:/QTZ:`. The display updates both on local panel edits and on incoming automation/synth changes. Initial implementation = multiline text with a fixed-width font (owner decision); hardware-accurate VFD rendering (dot-matrix glyphs, reference `VacuumFluoDisplayControl`) is specified by RQ-GUI-033/ADR-JUC-007. *Not yet ported: the trailing `.` active-modulation-destination marker (needs live page-family state).*
- **RQ-GUI-021** — Under the display, the UI shall provide the 8 reference shortcut buttons: program − / program +, goto patch, randomize, load patch, save patch, store patch, MIDI settings — each triggering the same controller operation as its menu counterpart.
- **RQ-GUI-022** — The UI shall display MIDI activity as the reference `LedPanelControl`: **three** square LEDs under the display, one per traffic source, each flashing on the MIDI-activity event (RQ-CTL-027) of its device — LED 1 = automation (controller) input, green RGB(144,255,144); LED 2 = synth input, blue RGB(92,171,255); LED 3 = synth output, red RGB(255,64,32). Geometry per the reference: 5 px squares evenly spaced in the extracted panel bounds (32×8 at 1190,150), vertically centered, 1 px border RGB(44,44,52), off-state fill RGB(54,54,62), transparent panel background. A LED shall stay lit ≈100 ms after the last event of its source and re-arm on every new event (continuous traffic keeps it lit); timing mechanics per ADR-JUC-008.

- **RQ-GUI-063** *(specified 2026-08-10, session GUI — owner request: replace the .NET bitmap leftovers)* — **Shortcut buttons drawn as vectors.** **Category:** Functional. **EARS type:** Ubiquitous. The eight shortcut buttons of RQ-GUI-021 SHALL be drawn from `juce::Path` geometry, and the application SHALL carry no raster asset for them. The 24 GIF resources (`minus`, `plus`, `gotopatch`, `random`, `load`, `save`, `store`, `settings`, each with its `hover` and `down` variant) SHALL be removed from the binary data.
  *Rationale:* they are the last raster elements of the control surface — the background, the knobs and the VFD are already vector — and they do not scale: at 1.25x and above they are interpolated and blur while everything around them stays crisp, which RQ-GUI-005's uniform-scale model otherwise guarantees. At 19x15 they are also too small to carry a legible glyph, which is why `random` reads as `?` and `load` as `...`. **Priority:** Must. **Dependencies:** RQ-GUI-021, RQ-GUI-005, RQ-SCL-001; RQ-DSN-010, ADR-JUC-014, ADR-JUC-017, ADR-GUI-001.
  - **Acceptance (Gherkin):** *Given* the built application, *When* its binary data is listed, *Then* no button GIF remains. *Given* the button row at 1x and at 2x, *When* the two renders are compared, *Then* the icon edges are sharp at both scales.

- **RQ-GUI-064** *(same session)* — **The icon set, and its legibility floor.** **Category:** Functional. **EARS type:** Ubiquitous. Each button SHALL carry one icon, drawn as an outline: **prev** a left triangle, **next** a right triangle, **goto** a right arrow meeting a vertical stop bar, **random** a die showing five pips, **load** an open folder (back panel with tab, front panel a parallelogram leaning left as it descends), **save** a floppy disk, **store** the same floppy in the accent red, **settings** a DIN-5 socket — circle, keyway notch interrupting it at the top, five pins on the lower arc.
  - Strokes SHALL be rendered with **rounded end caps and curved joints** (`juce::PathStrokeType`), never the default square cap: at this size a mitred or butt corner reads as a burr.
  - Every icon SHALL remain identifiable at the **1x display scale** (RQ-SCL-001), which is the legibility floor this requirement fixes — not "at some scale".
  *Rationale:* the icon language follows the owner's mockup; the two departures are recorded deliberately. **load** was absent from the mockup (it is the current `...` button) and takes a folder rather than a third floppy, which would be indistinguishable from `save` and `store` at 29 px. **settings** keeps the mockup's DIN rather than a gear, on owner instruction, with the pin count kept at five. **Priority:** Must. **Dependencies:** RQ-GUI-063, RQ-GUI-021, RQ-DSN-010, ADR-GUI-001.
  - **Acceptance (Gherkin):** *Given* the eight icons, *When* each is rendered at 1x, *Then* each is distinguishable from the other seven. *Given* any icon stroke, *When* its ends and corners are inspected, *Then* they are rounded.

- **RQ-GUI-065** *(same session)* — **The button row spans the modulation grid, exactly.** **Category:** Functional. **EARS type:** Ubiquitous. The eight buttons SHALL be square, of side `tokens::component::shortcutButtonSize`, separated by `shortcutButtonGap`, and the row SHALL start on the left edge of the `MOD_SRC_n` combo column and finish on the right edge of the `MOD_QUANTIZE_n` tick-box column — the same span RQ-CLR-007 already gives the `MOD MATRIX` separator. Across that 258 px this admits one sensible integer solution — 27 px keys, 6 px gaps — and the requirement is the **alignment**, not those two numbers.
  - The row SHALL sit `shortcutButtonGapAbove` below the MIDI LED strip and clear of it, the remaining space falling below the row.
  *Rationale:* the row currently spans 194 px inside a 267 px column and floats. An earlier draft tied it to the VFD's own edges; the owner pointed out that the modulation grid is the better reference, since the `MOD MATRIX` separator is already defined by it — so the whole right column now hangs off one grid instead of two, and the row, the separator and the twenty matrix rows all share their two verticals. The gap is small above and large below because the buttons belong to the display group (ADR-JUC-024), not to the matrix beneath — the proximity principle of RQ-CLR-001. **Priority:** Must. **Dependencies:** RQ-GUI-063, RQ-GUI-022, RQ-CLR-001, RQ-CLR-007, ADR-JUC-024, ADR-GUI-001.
  - **Acceptance (Gherkin):** *Given* the button row, *When* its two ends are compared with the VFD's, *Then* they coincide. *Given* the row and the LED strip, *When* their bounds are compared, *Then* they do not intersect.

- **RQ-GUI-066** *(same session)* — **The modulation matrix descends to meet the section rhythm.** **Category:** Functional. **EARS type:** Ubiquitous. The modulation matrix block — its four column labels and its twenty rows — SHALL be displaced downwards so the `MOD MATRIX` separator clears the block's lowest element by `tokens::component::sectionGapAbove`, as RQ-CLR-001 already requires of every other section.
  *Rationale:* the matrix column was never brought into the rhythm: TASK-CLR-001 and TASK-CLR-002 covered the left and centre columns only, and `SectionRhythmTests` did not assert this one, so a 43 px gap survived where the rule says 16. The correction is 27 px, and it is **derived from RQ-CLR-001, not chosen** — it happens to free exactly the room the taller button row needs, which is why the two changes travel together. **Priority:** Must. **Dependencies:** RQ-CLR-001, RQ-CLR-003, RQ-GUI-065, ADR-CLR-001, ADR-GUI-001.
  - **Acceptance (Gherkin):** *Given* the matrix column, *When* the gap between its lowest element and the `MOD MATRIX` label baseline is measured, *Then* it equals `sectionGapAbove`. *Given* `SectionRhythmTests`, *When* it runs, *Then* it asserts that gap for the matrix column as it does for the other seven sections.

- **RQ-GUI-067** *(specified 2026-08-10, session GUI — owner request)* — **A hovered shortcut key lights up in the control accent, like every other control.** **Category:** Functional. **EARS type:** Event-driven. WHEN the pointer enters a shortcut button, the UI SHALL draw that button's icon and outline in `XplorerLookAndFeel::ledColour()` brightened by `tokens::semantic::hoverBrighten` — the exact treatment a rotary knob, a tick box and a radio button already receive. The colour SHALL be read from the LookAndFeel at paint time and SHALL NOT be a token: `ledColour` is the single runtime source of truth for the control accent (ADR-JUC-011) and the user can retheme it (ADR-JUC-020), so a token would strand these eight keys on a fixed colour while everything around them followed the user's choice.
  - **Exception, `btPatchStore`.** Its ICON already carries `indicatorSynthOut` because it writes to the hardware. On hover the icon SHALL brighten in **its own red** rather than take the accent: the destructive-action signal outranks the hover signal. Its OUTLINE still lights in the accent like every other key, so the hover itself is never ambiguous.
  - The pressed state SHALL stay as it is — fill and ink inverted — so pressing reads differently from hovering rather than as more of it.
  *Rationale:* a first pass lit the keys in the synth-input MIDI blue, reading "LED colour" as the lamp's colour; the owner clarified that the intent was the interaction highlight the knobs, tick boxes and radios use. That distinction matters beyond the hue — the lamp colours are fixed constants, the control accent is user-themeable, and only the second keeps the row consistent with the panel after a retheme. **Priority:** Should. **Dependencies:** RQ-GUI-063, ADR-JUC-011, ADR-JUC-017, ADR-JUC-020, ADR-GUI-001.
  - **Acceptance (Gherkin):** *Given* any shortcut button other than store, *When* the pointer is over it, *Then* its icon and outline take the LookAndFeel's accent, brightened. *Given* a retheme that changes `ledColour`, *When* a button is hovered, *Then* its highlight follows the new colour. *Given* the store button, *When* the pointer is over it, *Then* its icon stays red and brightens while its outline takes the accent. *Given* any button, *When* it is held down, *Then* it renders inverted, not hovered.

Recorded here so the gap is not mistaken for an oversight.

## Controls & look

- **RQ-GUI-030** — Initial phase: standard JUCE controls (rotary `Slider`, `ComboBox`, `ToggleButton`, buttons) positioned on the logical canvas; behavior complete (owner decision).
- **RQ-GUI-031** — Skin phase (after functional parity): a custom `LookAndFeel` shall reproduce the reference control appearance — knobs with configurable LED ring/border color, linear/rotary mouse modes and standard/vintage styles (UiConfiguration, RQ-SET-003), image shortcut buttons (existing GIF assets), custom checkboxes/radio panels, VFD-style display (detailed by RQ-GUI-033). The rotary knob shall render as the coloured LED ring only — **no** centre-to-ring pointer/tick line (owner decision, cleaner than the reference Standard style), and **no filled knob body**: the interior is left transparent so the panel background (with its shading) shows through the ring — and shall brighten its ring while the mouse is over or dragging it (reference `_isMouseEntered` highlight).
  - *Amended 2026-08-06 (owner report, session GUI) — the "standard/vintage styles" switch is removed, closing the item ADR-JUC-009 explicitly left deferred.* ADR-JUC-009 (2026-07-13) already decided the app renders **only** the ring-only knob described above, regardless of any style setting — its own "Not in scope / deferred" note said the `UiConfiguration` Standard/Flat switch was "unaffected," not that it did anything. Confirmed by reading every consumer of `knobStyleIsStandard` before removing it: the Settings dialog's "Knob style" radio pair (`Standard`/`Flat`) read and wrote the field, and `XmlSettingsService` persisted it, but **no rendering code anywhere read it** — the toggle changed nothing on screen no matter its state. A user-facing choice with no effect is worse than no choice at all, so the switch — UI radios, the persisted field, and the XML read/write — is removed outright; the ring-only style (previously "Flat") is the sole, unconditional behaviour, with nothing left to choose. **Dependencies:** ADR-JUC-009 (DEC-JUC-106); RQ-SET-003 (amended in step).
- **RQ-GUI-034** — Rotary knobs shall not show a permanent numeric text box under the control (the value is already on the VFD, RQ-GUI-020; the reference shows none either). Instead: the value appears as a transient popup bubble while the knob is being turned, and a double-click opens an inline numeric entry to type an exact value. - **RQ-GUI-049** — **The display SHALL render the whole printable ASCII range 32–126.** The inherited sprite sheet implements only **51** of those 95 cells: `! " # $ % & < > ? @ \ ^ \` { | } ~` **and all 26 lowercase letters** are blank cells, byte-identical to the space cell. Any such character reaching the display therefore renders as nothing, silently. This is reachable today: `Dialogs.cpp` uppercases a patch name on *rename*, but `XpanderController::toneName()` — a name read from the synthesizer or from a `.syx` file — is not normalised anywhere before `VfdDisplayHelper::toneLine()` formats it. Characters outside 32–126 SHALL continue to render as a space. *Rationale:* a display that drops characters without any indication is a correctness defect, not a cosmetic limit; the segment table adopted by ADR-JUC-023 covers the full range at no extra cost, so the fix is a consequence of the port rather than extra work.
  - **No two distinct code points in 32–126 SHALL render identically** (owner decision, 2026-07-30). The vendored segment table holds **two** collisions, both resolved by the off-model primitives of DEC-JUC-052 rather than by editing the vendored data: `':'` and `'|'` share the two centre verticals (`0x2200`), and `'x'` and `'X'` share the four diagonals (`0x5500`). The colon override was already required for fidelity — the reference draws it as two dots — so it resolves its collision as a side effect and leaves `'|'` correctly rendered as a bar; lowercase `'x'` gains a half-height primitive. *Why this needs saying:* a 16-segment cell draws lowercase in its lower half, which works for 25 letters but not for `'x'`: a crossing needs one `\` and one `/` stroke, and both available diagonal pairs start at the **top** corners (`K`,`N`), so no lower-half crossing exists — the distinction cannot come from the segment topology and must be an explicit primitive. **Dependencies:** RQ-GUI-020, RQ-GUI-033; ADR-JUC-023 (DEC-JUC-051, DEC-JUC-052).

### Interaction feedback states

Today only the rotary knob reacts to the pointer (`drawRotarySlider` checks `isMouseOverOrDragging`); check boxes, radios and combo boxes render a single static state (`drawToggleButton` discards the `shouldDrawButtonAsHighlighted`/`shouldDrawButtonAsDown` parameters it receives and hardcodes `false, false`; `drawTickBox` receives `isEnabled` but ignores it; no component reads `hasKeyboardFocus`). Image shortcut buttons (`juce::ImageButton`) are **excluded** from this gap: they already have working hover/pressed feedback via dedicated reference `*hover.gif`/`*down.gif` assets (`MainComponent::createShortcutButtonsAndDisplay`, `setImages(...)`) — a different, already-complete mechanism, not covered by the requirements below. The following requirements close the "States missing" rows of the design-system component catalogue (RQ-DSN §4) on the GUI side. They add **no** new control and do **not** change any block layout — purely the per-state rendering of controls already placed.

- **RQ-GUI-041** *(implemented — architecture: ADR-JUC-017, TASK-JUC-109/110/111; combo hover-repaint gap fixed by TASK-HLT-001, issue #21)* — **EARS type: Event-driven.** WHEN the pointer is over an enabled interactive control — toggle button, check box, radio button, combo box, and `SettingsDialog` automation-table row — the control SHALL show a hover state using the **same** accent + `motion.hoverBrighten` rule as the rotary knob, so hover feedback reads as one consistent affordance across every control type instead of the knob-only reaction today. Image shortcut buttons are out of scope (already implemented, see the section note above). *Rationale:* the panel currently feels inert under the mouse; consistent hover is both a usability and a design-system-consistency fix already mandated for these controls but not implemented. **Dependencies:** RQ-GUI-030, RQ-GUI-031; RQ-DSN-023, RQ-DSN-030, RQ-DSN-031, RQ-DSN-061, RQ-DSN-062, ADR-JUC-014.
  - **Acceptance (Gherkin):** *Given* an enabled check box/combo/radio button, *When* the pointer enters it, *Then* it brightens by the shared `motion.hoverBrighten` factor (same visible amount as a hovered knob); *When* the pointer leaves, *Then* it returns to its idle appearance. *Given* a disabled control, *When* the pointer enters it, *Then* no hover brighten is shown.

- **RQ-GUI-055** *(specified — architecture: ADR-JUC-030; supersedes the splash-screen item of RQ-GUI-025)* — **No splash screen at startup.** **EARS type: Unwanted-behavior.** IF the application is launched, THEN it SHALL NOT display a splash screen, a startup image, or any transient window preceding the main window; the main window SHALL be the first and only window shown.
  - **Root cause this removes (owner report, 2026-08-04, Windows).** For about one second at launch, two panels are visible at once, offset and differently coloured. The splash is `LOGICAL_CANVAS_WIDTH × LOGICAL_CANVAS_HEIGHT` (1260×786) while the window is `windowSizeForScale(1.0)` (1440×922, RQ-SCL-001) — hence the offset — and the splash paints `defaultBlockPalette()` while the window behind paints the user's palette (RQ-DSN-095) — hence the colour difference.

It is no longer: the façade is now vector, resizable across five scale presets (RQ-SCL-002) and re-themable per user (RQ-GUI-046, RQ-DSN-095). A splash that mirrors the panel therefore **cannot** match the window that follows it, at any delay — the mismatch is structural, not a matter of timing. Every property that made that work has since been removed by later requirements. Keeping it costs a visible startup defect and a second, permanently-stale copy of the façade; removing it costs a startup image that no longer shows anything the user is about to see anyway. Startup is under a second, so nothing is being masked. **Priority:** Must. **Dependencies:** RQ-GUI-025, RQ-GUI-005, RQ-GUI-037, RQ-GUI-046, RQ-SCL-001, RQ-SCL-002, RQ-DSN-095; ADR-JUC-013, ADR-JUC-020, ADR-JUC-025, ADR-JUC-030.
