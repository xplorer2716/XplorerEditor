# RQ-GUI — User Interface (JUCE)

Scope: JUCE reimplementation of the WinForms View layer (MainForm, dialogs, MidiApp.UIControls).
Inputs: reference screenshot + owner's textual description (2026-07), `MainForm.Designer.cs` (4487 lines, 234 custom controls), `MainForm.resx` (background bitmap + button icons).
Owner decisions (2026-07): reuse the existing background bitmap; **resizable** main window; functional parity with standard JUCE controls first, custom skin afterwards.

## Main window — global structure

- **RQ-GUI-001** — The main window shall present all single-patch parameters simultaneously on one screen, laid out over the reference background image (block diagram of the synth signal path), organized as: LEFT column = VCO1, VCO2, FM/VCA, LAG, TRACK X blocks; CENTER column = MULTIMODE VCF/VCA1/VCA, ENV X, LFO X, RAMP X blocks; RIGHT column = VFD display, shortcut buttons, modulation matrix.
- **RQ-GUI-002** — The UI shall bind every control to its model parameter by name through a registration mechanism (control identifier → parameter name), so control changes call `SetParameter` and controller events update controls, with no per-control hand-written glue.
- **RQ-GUI-003** — When a parameter-change event arrives from the controller (automation or synth), the affected control shall update without echoing the change back to the synth.
- **RQ-GUI-004** — While a control is being edited from the UI, its mapped CC automation shall be temporarily disabled (RQ-FMW-033).
- **RQ-GUI-005** — The main window shall be freely **resizable**: the whole content (background bitmap and controls, positioned on a fixed logical canvas) scales uniformly with the window, preserving aspect ratio (owner decision; supersedes the reference's fixed launch-time DPI sizing).
- **RQ-GUI-006** — The UI shall run on the JUCE message thread; controller events arriving from other threads shall be marshalled to it (RQ-FMW-061) via the `EventDispatcher` seam.
- **RQ-GUI-007** — The main window shall use the reference background bitmap extracted from `MainForm.resx`, rendered scaled; a vector redraw is a post-parity evolution (ADR-JUC-006).
- **RQ-GUI-008** — The main window shall provide the reference menu bar: **File** (New, Open, Save, Save As, Exit), **Patch** (Next, Previous, Goto, Rename, Store, Randomize, Copy page, Paste page, Synchronize, Visualize), **Tools** (Settings, Tune Request, Single patches: Extract from bank / Get from synth, All data dump: Backup / Restore), **Help** (Help, Check for new release, Go to website, About) — plus, beyond the .NET reference, a **View** menu (scale presets 1x/1.25x/1.5x/1.75x/2x, Full Screen) added by RQ-SCL-002/RQ-SCL-003 for window-size/scale management, placed between **Patch** and **Tools** in the bar order.

## Page families (shared control blocks)

- **RQ-GUI-010** — The ENV X, LFO X, RAMP X and TRACK X areas shall each be a **single shared control block** whose controls edit the currently selected family instance; selector buttons (ENV 1–5, LFO 1–5, RAMP 1–4, TRACK 1–3) switch the active instance.
- **RQ-GUI-011** — When a selector button is clicked, the block's controls shall rebind to the selected instance's parameters (name = family prefix + digit, per `PageFamilyDescriptor`), refresh their displayed values from the model, and the controller shall send the matching page-select to the synth (reference `TriggerRuleManager`/`PageRefreshManager` behavior). Each selector button shall carry the reference caption — `ENV 1`…`ENV 5`, `LFO 1`…`LFO 5`, `RAMP 1`…`RAMP 4`, `TRACK 1`…`TRACK 3` (the `.Text` from `MainForm.resx`), not the bare instance digit.
- **RQ-GUI-012** — When the synth selects an ENV/LFO/RAMP/TRACK page (page-change event, RQ-CTL-023), the corresponding selector shall activate and the block shall refresh, mirroring the synth panel.

## Modulation matrix panel

- **RQ-GUI-015** — The matrix panel shall present the 20 modulation entries as 4 groups of 5 rows; each row = source combo box, amount knob (−63..+63), destination combo box, quantize checkbox (reference tags `MOD_SOURCE_n`, `MOD_AMNT_SRC_n`, `MOD_DEST_n`, `MOD_QUANTIZE_n`).
- **RQ-GUI-016** — Row edits shall call the controller matrix operations (RQ-CTL-030); destination combos shall only offer destinations allowed by the max-6-sources rule, and source editability shall follow `sourceAvailabilityForEntry`.
- **RQ-GUI-017** — Modulation-entry-change and full-tone-change events shall refresh the affected row(s)/whole matrix without echoing to the synth.
- **RQ-GUI-018** — The matrix shall highlight rows related to the control under the mouse, as the reference (`InitializeModSourceHighlight`): hovering a page-family selector that is a modulation source (ENV/LFO/RAMP/TRACK n) shall highlight every source combo currently set to that source; hovering a knob that is a modulation destination shall highlight every destination combo currently set to that destination **and** whose row has an active source (≠ NONE). The highlight clears on mouse-leave. Paged knobs (ENV/LFO) resolve their destination against the currently selected family instance.
  - *Amended 2026-08-03 (owner decision, session GUI) — the **rendering** of the highlight is superseded by RQ-GUI-052; the **trigger and row-selection rules above are unchanged**.* The original statement highlighted by repainting the combo's **background** with the knob LED-border colour. Both clauses are withdrawn: RQ-GUI-052 gives the combo's background a permanent meaning (the functional-block identity of its selected value), so repainting it on hover would erase that information for exactly as long as the user is looking at it, and the LED accent would sit on top of a block-coloured control it has no relation to. The highlight becomes a **frame** treatment instead (RQ-GUI-052), leaving the background untouched. *Rationale for keeping this requirement rather than merging it into RQ-GUI-052:* the cross-reference logic — which rows match, the ≠ NONE filter, the paged-instance resolution — is behaviour, is already implemented and headless-tested (`ModulationHighlight`), and is unaffected by how the result is drawn. **Dependencies:** RQ-GUI-052, RQ-CTL-030; ADR-JUC-010, ADR-JUC-028.

## VFD display & shortcut buttons

- **RQ-GUI-020** — The UI shall show a display area at top-right presenting at minimum: current program number and patch name, and the last edited parameter on change. The parameter line shall follow the reference `VfdDisplayHelper` content: the parameter's end-user display name (Resources.resx string, tag as fallback) and its value formatted by control type — combo/radio selection **label**, checkbox `Y`/`N`, knob numeric — plus the mapped `MIDI CC:` number when one exists — the reference's unassigned-CC sentinel (last entry of the CC name list, value 128) shall never be shown as if it were a real CC *(fixed TASK-JUC-089, issue #11)*; a modulation-matrix edit shall instead show `SRC TO DEST:` with `AMNT:/QTZ:`. The display updates both on local panel edits and on incoming automation/synth changes. Initial implementation = multiline text with a fixed-width font (owner decision); hardware-accurate VFD rendering (dot-matrix glyphs, reference `VacuumFluoDisplayControl`) is specified by RQ-GUI-033/ADR-JUC-007. *Not yet ported: the trailing `.` active-modulation-destination marker (needs live page-family state).*
- **RQ-GUI-021** — Under the display, the UI shall provide the 8 reference shortcut buttons: program − / program +, goto patch, randomize, load patch, save patch, store patch, MIDI settings — each triggering the same controller operation as its menu counterpart.
- **RQ-GUI-022** — The UI shall display MIDI activity as the reference `LedPanelControl`: **three** square LEDs under the display, one per traffic source, each flashing on the MIDI-activity event (RQ-CTL-027) of its device — LED 1 = automation (controller) input, green RGB(144,255,144); LED 2 = synth input, blue RGB(92,171,255); LED 3 = synth output, red RGB(255,64,32). Geometry per the reference: 5 px squares evenly spaced in the extracted panel bounds (32×8 at 1190,150), vertically centered, 1 px border RGB(44,44,52), off-state fill RGB(54,54,62), transparent panel background. A LED shall stay lit ≈100 ms after the last event of its source and re-arm on every new event (continuous traffic keeps it lit); timing mechanics per ADR-JUC-008.

## Dialogs & workflows

- **RQ-GUI-025** — The UI shall provide the reference dialog workflows: settings (MIDI / UI / randomizer pages), rename patch, store & goto patch, extract single tones from a bank file, tone morphing, progress display for long operations, about box, and ~~splash screen~~ *(splash screen struck 2026-08-04, session GFX — superseded by RQ-GUI-055, architecture ADR-JUC-030; every other workflow in this list is unaffected)*. **About box** *(implemented TASK-JUC-104)* — strongly inspired by the reference `AboutForm` (`Xplorer/View/AboutForm.Designer.cs`): a fixed-size white dialog with the reference `About.jpg` image (the VFD close-up photo, `Resources.About` → `xdata/About.jpg`) docked on the left edge, stretched to fill the height; on the right, the product title, the product name/version string, copyright notice, a clickable link to the project's GitHub repository, a separator, the GPL v3 licence notice, and a clickable link to the licence text. Clicking anywhere in the dialog outside the two links closes it, matching the reference's whole-form click-to-dismiss.
- **RQ-GUI-026** — Long operations (all-data dump backup/restore, get-all-patches) shall run off the message thread with progression display and shall keep the UI responsive (no event pumping); cancellation where the reference offers it.
- **RQ-GUI-027** *(implemented — TASK-JUC-088, issue #13)* — The UI shall provide the copy/paste page actions for ENV/LFO/RAMP/TRACK page-family instances via a right-click context menu on each family's instance-selector button ("Copy Page" / "Paste Page", reference `PageContextMenuStrip`), with Paste greyed out when ineligible (RQ-CTL-040: different family, or same instance as the copied one), plus the Ctrl+C / Ctrl+V keyboard equivalents while a selector button is focused. *Corrected 2026-07: the reference UX is this context menu, not a top-level Patch → Copy/Paste menu entry — the earlier wording of this requirement was inaccurate, per the "reference functional behavior is authoritative" rule.*
- **RQ-GUI-028** — The UI shall provide a piano-keyboard window sending Note On/Off to the synth (RQ-MID-010).
- **RQ-GUI-029** — The main window shall accept a dropped `.syx` file (reference `MainForm` `AllowDrop`): the first dropped `.syx` is classified (RQ-MOD-043) and loaded by type — a single tone replaces and transmits the edited tone (RQ-CTL-001), an all-data dump is restored after an explicit confirmation (with progress, RQ-GUI-026), an unknown file raises a warning. The File → Open menu shares the same load-by-type path.
- **RQ-GUI-036** — The MIDI settings page shall present the **CC automation table** as an editable list (reference `MidiPage` `LvAutomation`): one row per tone parameter, showing the parameter's friendly name and its assigned Continuous-Controller name; the user picks a CC per parameter from the reference CC-name list (index = CC number, last entry = unassigned), with a "reset all to unassigned" action. On accept the table is persisted (RQ-SET-002) **and** applied to the controller's automation dictionary. The persisted table shall also be loaded into the controller at startup and whenever settings change, so incoming CCs actually drive the mapped parameters (RQ-FMW-050..052) and the VFD shows the mapped CC (RQ-GUI-020) — the current build persists the table but never loads it. The page shall also offer an **"Export as HTML"** action (reference `MidiPage` HTML export) writing the current mapping to a self-contained, light, compact, print-friendly HTML file (Parameter / Control Change columns, title, project link, generation timestamp) and opening it in the default browser. Behaviour and CC-name set per ADR-JUC-012.

## Controls & look

- **RQ-GUI-030** — Initial phase: standard JUCE controls (rotary `Slider`, `ComboBox`, `ToggleButton`, buttons) positioned on the logical canvas; behavior complete (owner decision).
- **RQ-GUI-031** — Skin phase (after functional parity): a custom `LookAndFeel` shall reproduce the reference control appearance — knobs with configurable LED ring/border color, linear/rotary mouse modes and standard/vintage styles (UiConfiguration, RQ-SET-003), image shortcut buttons (existing GIF assets), custom checkboxes/radio panels, VFD-style display (detailed by RQ-GUI-033). The rotary knob shall render as the coloured LED ring only — **no** centre-to-ring pointer/tick line (owner decision, cleaner than the reference Standard style), and **no filled knob body**: the interior is left transparent so the panel background (with its shading) shows through the ring — and shall brighten its ring while the mouse is over or dragging it (reference `_isMouseEntered` highlight).
- **RQ-GUI-034** — Rotary knobs shall not show a permanent numeric text box under the control (the value is already on the VFD, RQ-GUI-020; the reference shows none either). Instead: the value appears as a transient popup bubble while the knob is being turned, and a double-click opens an inline numeric entry to type an exact value. Removing the text box lets the rotary fill its full extracted bounds, rendering slightly larger and closer to the reference proportions.
- **RQ-GUI-032** — Valued controls shall map integer parameter ranges exactly (min/max/step from the model), including signed ranges and enum-labeled combos (filter modes, wave shapes, sources/destinations) with the reference label sets. Combo box labels shall always render in full, never ellipsized *(TASK-JUC-087, issue #12; sizing rule superseded by RQ-GUI-047, issue #12 follow-up)*.
- **RQ-GUI-033** — The display SHALL render its text as **16-segment glyphs drawn vectorially**, on a black background, with the glyph block centered in the control bounds and the grid derived from those bounds (`cols = width/12`, `lines = height/16`, in *logical* units) — replacing the interim fixed-width-font rendering of RQ-GUI-020. Every glyph cell SHALL show the unlit segments as well as the lit ones, and lit segments SHALL carry the phosphor glow of the reference. Implementation choices (path construction, caching, the rendering scale) per ADR-JUC-023.
  - *Amended 2026-07-30 (owner decision, session VFD).* The original statement mandated bitmap glyphs blitted from the reference `MATRIXTINY` sprite sheet (96 cells of 12×16 px in a 32×3 grid), extracted mechanically from the .NET resources. **Both clauses are withdrawn**, for two independent reasons: (a) the sprite carries only 12×16 px of information per glyph, so it cannot stay crisp once the physical pixel scale leaves 1.0 — which happens on any HiDPI display and on any window enlargement (RQ-GUI-005) — and nearest-neighbour magnification (the previous mitigation) cannot invent detail that is not in the source; (b) the extraction clause became **unsatisfiable** when the .NET tree moved to `xplorer2716/XplorerEditor-dotnet-archive`: `extract_control_table.py` reads `Xplorer/Properties/Resources.resx`, a path that no longer exists in this repository, so the committed asset is no longer regenerable here. The *intent* of the requirement — an afficheur that reads as hardware VFD — is unchanged; only the means are. The interim sprite sheet remains valid until ADR-JUC-023 is implemented. **Dependencies:** RQ-GUI-005, RQ-GUI-020, RQ-GUI-031, RQ-GUI-049, RQ-DSN-097; ADR-JUC-023.
  - **Acceptance (Gherkin):** *Given* the display holds any text, *When* the panel is painted at a physical pixel scale of 1.0, 2.0 or 3.0, *Then* the glyphs are rasterised at that scale and no magnification of a fixed-size raster occurs. *Given* a glyph cell with no character to show, *When* it is painted, *Then* its unlit segments are visible at the reference's low intensity rather than a flat black cell. *Given* the repository, *When* the VFD is rendered, *Then* no `.png` sprite sheet is read for glyph artwork.

- **RQ-GUI-049** — **The display SHALL render the whole printable ASCII range 32–126.** The inherited sprite sheet implements only **51** of those 95 cells: `! " # $ % & < > ? @ \ ^ \` { | } ~` **and all 26 lowercase letters** are blank cells, byte-identical to the space cell. Any such character reaching the display therefore renders as nothing, silently. This is reachable today: `Dialogs.cpp` uppercases a patch name on *rename*, but `XpanderController::toneName()` — a name read from the synthesizer or from a `.syx` file — is not normalised anywhere before `VfdDisplayHelper::toneLine()` formats it. Characters outside 32–126 SHALL continue to render as a space. *Rationale:* a display that drops characters without any indication is a correctness defect, not a cosmetic limit; the segment table adopted by ADR-JUC-023 covers the full range at no extra cost, so the fix is a consequence of the port rather than extra work.
  - **No two distinct code points in 32–126 SHALL render identically** (owner decision, 2026-07-30). The vendored segment table holds **two** collisions, both resolved by the off-model primitives of DEC-JUC-052 rather than by editing the vendored data: `':'` and `'|'` share the two centre verticals (`0x2200`), and `'x'` and `'X'` share the four diagonals (`0x5500`). The colon override was already required for fidelity — the reference draws it as two dots — so it resolves its collision as a side effect and leaves `'|'` correctly rendered as a bar; lowercase `'x'` gains a half-height primitive. *Why this needs saying:* a 16-segment cell draws lowercase in its lower half, which works for 25 letters but not for `'x'`: a crossing needs one `\` and one `/` stroke, and both available diagonal pairs start at the **top** corners (`K`,`N`), so no lower-half crossing exists — the distinction cannot come from the segment topology and must be an explicit primitive. **Dependencies:** RQ-GUI-020, RQ-GUI-033; ADR-JUC-023 (DEC-JUC-051, DEC-JUC-052).
  - **Acceptance (Gherkin):** *Given* a tone name containing lowercase letters, *When* it is shown on the display, *Then* every letter is legible and none renders as a blank cell. *Given* each code point in 32–126, *When* it is rendered, *Then* the produced cell differs from the cell produced for a space — except for the space itself. *Given* all 95 code points in 32–126, *When* each is rendered, *Then* the 95 results are pairwise distinct — in particular `'x'` differs from `'X'` and `':'` differs from `'|'`. *Given* a code point outside 32–126, *When* it is rendered, *Then* it renders as a space.

- **RQ-GUI-050** — **The display SHALL be framed by a recessed bezel, and the display, its MIDI-activity LEDs and its shortcut buttons SHALL read as one group set apart from the panel.** Today the black glass sits directly on the brushed-metal plate with no transition: it is the only element of the façade with no frame, so it reads as pasted on rather than mounted in. Owner observation, 2026-07-31.
  - **Bezel.** A metal band around the glass, its top edge darkened and its bottom edge lit — the inverse of the raised-plate treatment used for labelled blocks (RQ-DSN-094) — so the light reads as coming from above and the glass as *sunk into* the plate. A flat bright outline was mocked up first and rejected: at 1:1 it was the highest-contrast element of the whole façade, louder than any block frame, and drew attention out of proportion to the display's importance.
  - **Group alignment.** The bezel's **top edge** SHALL align with the top of the VCF block row, so a single horizontal line reads across the façade. The LED strip and the shortcut buttons SHALL follow the display upward by the same amount, preserving the vertical gaps that separate them from it, so the three keep reading as one assembly.
  - **This requires a layout deviation, and that is the point.** The current geometry leaves **one pixel** between the glass (ending at y=122) and the LED strip (starting at y=123) — a bezel is geometrically impossible without moving something. The display group therefore departs from the mechanically-extracted reference coordinates (RQ-GUI-001, ADR-JUC-006) and from RQ-GUI-037's "reproduces the reference layout" clause. Both deviations are **owner-arbitrated and deliberate**, and follow the precedent of TASK-GUI-009 (VCO2 checkbox row) — the control table is the source of truth now that the .NET tree is archived, so the deviation is recorded there rather than left as an unexplained offset in placement code.
  - **Design-system compliance.** Every visual value — band gradient stops, corner radius, margins, shadow and highlight alphas — SHALL come from design-system tokens (RQ-DSN-098), with no raw literal in code. The lateral margin MAY differ from the vertical one: the mockup showed the bezel crowding the modulation matrix on its right while having air above.
  **Dependencies:** RQ-GUI-001, RQ-GUI-020, RQ-GUI-022, RQ-GUI-033, RQ-GUI-037, RQ-DSN-094, RQ-DSN-098; ADR-JUC-006, ADR-JUC-013, ADR-JUC-024.
  - **Acceptance (Gherkin):** *Given* the main window at the launch geometry, *When* it is painted, *Then* the display is surrounded by a bezel whose top edge is level with the top of the VCF block row. *Given* the bezel, *When* its edges are compared, *Then* the top edge is darker than the band and the bottom edge lighter, so the glass reads as recessed. *Given* the display group, *When* the gaps between the bezel, the LED strip and the shortcut buttons are measured, *Then* they are unchanged from before the lift. *Given* the renderer source, *When* it is read, *Then* no bezel colour, radius, margin or alpha appears as a literal. *Given* the control table, *When* the display-group entries are read, *Then* the lifted coordinates are recorded there with their rationale, not applied as an offset at placement time.

### Interaction feedback states

Today only the rotary knob reacts to the pointer (`drawRotarySlider` checks `isMouseOverOrDragging`); check boxes, radios and combo boxes render a single static state (`drawToggleButton` discards the `shouldDrawButtonAsHighlighted`/`shouldDrawButtonAsDown` parameters it receives and hardcodes `false, false`; `drawTickBox` receives `isEnabled` but ignores it; no component reads `hasKeyboardFocus`). Image shortcut buttons (`juce::ImageButton`) are **excluded** from this gap: they already have working hover/pressed feedback via dedicated reference `*hover.gif`/`*down.gif` assets (`MainComponent::createShortcutButtonsAndDisplay`, `setImages(...)`) — a different, already-complete mechanism, not covered by the requirements below. The following requirements close the "States missing" rows of the design-system component catalogue (RQ-DSN §4) on the GUI side. They add **no** new control and do **not** change any block layout — purely the per-state rendering of controls already placed.

- **RQ-GUI-041** *(implemented — architecture: ADR-JUC-017, TASK-JUC-109/110/111; combo hover-repaint gap fixed by TASK-HLT-001, issue #21)* — **EARS type: Event-driven.** WHEN the pointer is over an enabled interactive control — toggle button, check box, radio button, combo box, and `SettingsDialog` automation-table row — the control SHALL show a hover state using the **same** accent + `motion.hoverBrighten` rule as the rotary knob, so hover feedback reads as one consistent affordance across every control type instead of the knob-only reaction today. - **RQ-GUI-054** *(specified — architecture: ADR-JUC-029; supersedes RQ-GUI-042 and the focus half of RQ-DSN-033)* — **No keyboard-focus visual indicator.** **EARS type: Unwanted-behavior.** IF an interactive control holds keyboard focus, THEN the application SHALL NOT render any visual indicator of that focus — no ring, outline, underline, fill change, brighten or any other treatment distinguishing the focused control from its unfocused idle appearance.
  - **Scope — rendering only.** Keyboard *focusability* is untouched: `juce::Button` / `juce::ComboBox` keep accepting focus, tab traversal keeps working mechanically, and every control keeps its keyboard behaviour — in particular `PageSelectorButton::setWantsKeyboardFocus(true)`, which exists so Ctrl+C/Ctrl+V reach `keyPressed` (RQ-GUI-027), SHALL remain. This requirement removes an *appearance*, not an *access path*: no control becomes unreachable by keyboard.
  - **The other two interaction states are unaffected.** Hover (RQ-GUI-041) and Disabled (RQ-GUI-043) SHALL keep their current shared treatments, unchanged in rule and in value. This requirement removes exactly one of the three states of ADR-JUC-017, and the removal SHALL NOT be implemented by folding focus into hover — a focused-but-not-hovered control SHALL be indistinguishable from an idle one.
  - **The design system SHALL carry no orphan focus vocabulary.** The `semantic.strokeFocusRing` role, introduced for this indicator alone (RQ-DSN-099, ADR-JUC-028 DEC-JUC-083), SHALL be removed from `juce/tools/design-tokens.yaml` — the single source of truth (RQ-DSN-063) — so no unused visual role survives its only consumer, and the design system cannot be read as still specifying a focus treatment. No other token changes: `strokeBorder`, `strokeDiagram` and `strokeLine` keep their current values and their remaining consumers.
  - **The shared focus-ring geometry rule goes with it.** `focusRingInside()` (ADR-JUC-028 DEC-JUC-084) exists only to place a focus ring beside a border and SHALL be removed with its four call sites. The *frame* half of DEC-JUC-084 — a stroked rectangle inset by half its own stroke width, so a 1.5 px highlight is not clipped against the component bounds — is a general rule about strokes, not about focus, and SHALL be preserved.

  *Rationale:* the indicator was implemented under RQ-GUI-042, then reworked twice under ADR-JUC-028 (DEC-JUC-083 to stop it hiding the block-identity borders of RQ-GUI-045/RQ-GUI-052, DEC-JUC-084 to correct its corner geometry). After both, the owner's assessment (2026-08-04) is that it still reads badly and conflicts graphically with the rest of the GUI: on a matrix combo or a page-family selector the ring is a **fourth** frame meaning stacked on controls that already carry block identity, cross-reference highlight and their own border — one competing rectangle too many, which is the boundary ADR-JUC-028's own Consequences section named ("a fourth would need a rethink rather than another width or another inset"). The rethink is that the indicator does not earn its place. **The accessibility argument is answered, but only in part, and knowingly:** RQ-GUI-042 justified itself against a UI that reports nothing, and this one is not that — the VFD shows the last control acted upon (RQ-GUI-020), so a user driving the panel by keyboard does get positional feedback from their own actions. It is **not** an equivalent: it reports the last *action*, not the current focus *position*, so a user tabbing across controls without acting has no cue at all. That residual gap is the accepted cost of this requirement, recorded rather than argued away. **Priority:** Must. **Scope:** rendering only — no control geometry, layout, binding, controller or list-content change; no new token, no replacement indicator. **Dependencies:** RQ-GUI-041, RQ-GUI-043, RQ-GUI-045, RQ-GUI-052, RQ-GUI-020, RQ-GUI-027; RQ-DSN-030, RQ-DSN-033, RQ-DSN-062, RQ-DSN-063, RQ-DSN-099; ADR-JUC-014, ADR-JUC-015, ADR-JUC-017, ADR-JUC-019, ADR-JUC-028, ADR-JUC-029.
  - **Acceptance (Gherkin):** *Given* any check box, radio button, combo box or page-family selector button, *When* it holds keyboard focus, *Then* it renders exactly as it does when it does not hold focus, with no added ring, outline or other cue. *Given* a focused modulation-matrix combo box, *When* it is rendered, *Then* its block-identity frame (RQ-GUI-052) is the only frame it carries. *Given* a focused page-family selector button, *When* it is rendered, *Then* its block-hue border (RQ-GUI-045) is the only border it carries. *Given* an enabled control, *When* the pointer enters it, *Then* the RQ-GUI-041 hover brighten still applies; *Given* a disabled control, *When* it is rendered, *Then* the RQ-GUI-043 treatment still applies. *Given* the main window, *When* the user presses Tab repeatedly, *Then* focus still moves between controls and Ctrl+C / Ctrl+V on a page-family selector still copy and paste the page (RQ-GUI-027). *Given* `juce/tools/design-tokens.yaml` and the generated `DesignTokens.hpp`, *When* they are searched for `strokeFocusRing`, *Then* there is no match; *Given* the application sources, *When* they are searched for `hasKeyboardFocus` and `focusRingInside`, *Then* there is no match.

- **RQ-GUI-055** *(specified — architecture: ADR-JUC-030; supersedes the splash-screen item of RQ-GUI-025)* — **No splash screen at startup.** **EARS type: Unwanted-behavior.** IF the application is launched, THEN it SHALL NOT display a splash screen, a startup image, or any transient window preceding the main window; the main window SHALL be the first and only window shown.
  - **Root cause this removes (owner report, 2026-08-04, Windows).** For about one second at launch, two panels are visible at once, offset and differently coloured. They are not a rendering artefact: they are two genuinely painted surfaces. `initialise()` creates a `juce::SplashScreen` with `deleteAfterDelay(2s)` **and** the `MainWindow` immediately after, so both are on screen for the whole delay, splash on top. The splash is `LOGICAL_CANVAS_WIDTH × LOGICAL_CANVAS_HEIGHT` (1260×786) while the window is `windowSizeForScale(1.0)` (1440×922, RQ-SCL-001) — hence the offset — and the splash paints `defaultBlockPalette()` while the window behind paints the user's palette (RQ-DSN-095) — hence the colour difference.
  - **Why removal rather than a shorter or better-aligned splash.** The splash is drawn by `paintVectorBackground`, the *same* painter as the main panel (ADR-JUC-013), so it is a pixel-faithful copy of the façade. That was coherent when the façade was one fixed bitmap (`main-background.jpg`) at one size with one palette. It is no longer: the façade is now vector, resizable across five scale presets (RQ-SCL-002) and re-themable per user (RQ-GUI-046, RQ-DSN-095). A splash that mirrors the panel therefore **cannot** match the window that follows it, at any delay — the mismatch is structural, not a matter of timing. And because it is a near-copy rather than a distinct logo, the overlap does not read as "splash, then app"; it reads as a rendering defect.
  - **Scope.** `Main.cpp` only: the splash image, its `paintVectorBackground` call and the `juce::SplashScreen` instance. No change to the main window, its launch size (RQ-SCL-001), the vector painter, the block palette, the single-instance guard (RQ-FMW-072) or the top-level exception dialog (RQ-GUI-035). `paintVectorBackground` keeps its palette parameter — it has a second, live caller in `MainComponent::paint`.

  *Rationale:* the splash existed to mirror the reference `MainForm` startup image, and the reference's splash *was* the panel bitmap. Every property that made that work has since been removed by later requirements. Keeping it costs a visible startup defect and a second, permanently-stale copy of the façade; removing it costs a startup image that no longer shows anything the user is about to see anyway. Startup is under a second, so nothing is being masked. **Priority:** Must. **Dependencies:** RQ-GUI-025, RQ-GUI-005, RQ-GUI-037, RQ-GUI-046, RQ-SCL-001, RQ-SCL-002, RQ-DSN-095; ADR-JUC-013, ADR-JUC-020, ADR-JUC-025, ADR-JUC-030.
  - **Acceptance (Gherkin):** *Given* the application is launched, *When* the first window appears, *Then* it is the main window at `windowSizeForScale(1.0)` and no other window is or was shown. *Given* a user with customised block colours, *When* the application starts, *Then* no panel is ever painted in the default palette. *Given* the sources, *When* they are searched for `SplashScreen`, *Then* there is no match. *Given* the main window, *When* it is displayed, *Then* its background, scaling, menu bar and controls are unchanged from before this requirement.
