# RQ-BLD — Build System & Tooling

- **RQ-BLD-001** — The C++ implementation shall build with CMake (≥ 3.22) fetching JUCE 8.x as a pinned dependency, with no manually-copied binaries.
- **RQ-BLD-002** — The primary target platform shall be Windows (x64); the non-UI layers (MID, FMW, MOD, CTL, SET) shall also compile and run their tests headless on Linux. *Amended 2026-07-29: macOS (arm64) is added as an additional CI-covered GUI-app build target — see RQ-BLD-011/RQ-BLD-012 — without changing Windows' status as the primary target.*
- **RQ-BLD-003** — The code shall use C++20, compile warning-clean at high warning levels (/W4, -Wall -Wextra) with warnings-as-errors for project code.
- **RQ-BLD-004** — The C++ tree shall live in this repository under a dedicated top-level directory, leaving the .NET solution untouched and buildable during the whole migration.
- **RQ-BLD-005** — A single CMake invocation shall build libraries per layer (midi, framework, model, controller, settings), the application, and the test executables.
- **RQ-BLD-006** — All source files shall carry the GPL v3 header of the reference project; JUCE shall be used under its GPL option (no commercial JUCE license assumed).
- **RQ-BLD-007** — CI shall build and run the non-UI test suite on every push (GitHub Actions, Linux at minimum).
- **RQ-BLD-010** — Each CI build workflow SHALL cover exactly one build configuration, and its **file name, workflow name and job name SHALL be identical**, formed as `<os>-<application>-<build>` — e.g. `linux-headless-release`, `windows-app-release`, `windows-app-debug`. *Rationale:* a status check in a pull request then names its own os/target/configuration without cross-referencing, and a workflow file can never hide a second, differently-configured job under an unrelated name (owner requirement, 2026-07-29). *Acceptance (Gherkin):* Given any workflow under `.github/workflows/`, When it is read, Then its `name:`, its single job key and its file stem are the same `<os>-<application>-<build>` string.
- **RQ-BLD-008** — The Windows (x64) GUI binary shall be produced with the MSVC toolchain. JUCE does not support MinGW (`juce_TargetPlatform.h` `#error`s on `__MINGW32__`), so cross-compiling the GUI app from Linux with MinGW-w64 is not viable; the amd64 `Xplorer.exe` is built by a native Windows CI job (`.github/workflows/windows-app-release.yml`) that also runs the unit suite and uploads the binary as an artifact.
- **RQ-BLD-009** — **EARS type: Event-driven.** WHEN a push lands on the `main` branch and the Windows CI build succeeds, the pipeline SHALL publish the resulting `Xplorer.exe` as a GitHub Release explicitly marked **pre-release**, distinctly tagged from production releases so it can never be mistaken for one (RQ-BLD-002/008 remain the production-build requirements, unaffected). The release notes SHALL be a concise summary of the changes (commit subjects) landed on `main` since the previous alpha release. *Rationale:* gives the owner/testers a continuously up-to-date, clearly-labelled preview build without polluting the production release stream. **Dependencies:** RQ-BLD-002, RQ-BLD-008.
  - **Acceptance (Gherkin):** *Given* a push to `main`, *When* the Windows build succeeds, *Then* a GitHub Release is created with `prerelease: true`, a tag distinct from production tags (e.g. `vX.Y.Z`), and `Xplorer.exe` attached. *Given* the same push, *When* the release is created, *Then* its notes list the commits landed since the previous alpha release, not the full project history. *Given* a production release is cut, *When* the Releases page is viewed, *Then* alpha releases are visually distinguishable (pre-release badge) and never the "Latest" one.
- **RQ-BLD-011** — **EARS type: Event-driven.** WHEN a push or pull request touches `juce/**`, CI SHALL build the JUCE GUI application for macOS (arm64) in Release configuration and upload the resulting `.app` bundle as a downloadable GitHub Actions artifact — mirroring RQ-BLD-008's Windows build, but without publishing a GitHub Release (owner decision, scope kept to a CI artifact for now; RQ-BLD-009/ADR-BLD-001's alpha-release stream stays Windows-only). *Rationale:* the JUCE GUI app targets macOS as a real user platform, and a downloadable Release-config build lets the owner validate it without a local toolchain. **Dependencies:** RQ-BLD-002, RQ-BLD-010, ADR-BLD-002.
  - **Acceptance (Gherkin):** *Given* a push or pull request touching `juce/**`, *When* `macos-app-release.yml` runs on `macos-latest` (arm64), *Then* the build succeeds in Release configuration and the produced `Xplorer.app` bundle is uploaded as a CI artifact. *Given* the same run, *When* it completes, *Then* no GitHub Release is created (artifact-only, unlike the Windows workflow).
- **RQ-BLD-012** — **EARS type: Event-driven.** WHEN a push or pull request touches `juce/**`, CI SHALL also build the JUCE GUI application for macOS (arm64) in Debug configuration with tests enabled, running the full suite including the real-metrics combo-box fit check (`xpl_tests_app_juce`) against macOS's own font-rendering stack — extending the cross-platform fit guarantee of RQ-GUI-047/RQ-GUI-048/RQ-DSN-096 to a third platform, mirroring `windows-app-debug`. **Dependencies:** RQ-GUI-047, RQ-GUI-048, RQ-DSN-096, ADR-JUC-022, ADR-BLD-002.
  - **Acceptance (Gherkin):** *Given* a push or pull request touching `juce/**`, *When* `macos-app-debug.yml` runs on `macos-latest` (arm64), *Then* the build succeeds in Debug configuration with `XPL_BUILD_TESTS=ON` and `ctest` runs every suite, including `xpl_tests_app_juce`, to completion. *Given* a combo-box label that would overflow at the shipped size on macOS's real font metrics, *When* this workflow runs, *Then* `xpl_tests_app_juce` fails the build (not just logs).
