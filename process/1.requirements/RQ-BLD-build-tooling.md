# RQ-BLD — Build System & Tooling

- **RQ-BLD-001** — The C++ implementation shall build with CMake (≥ 3.22) fetching JUCE 8.x as a pinned dependency, with no manually-copied binaries.
- **RQ-BLD-002** — The primary target platform shall be Windows (x64); the non-UI layers (MID, FMW, MOD, CTL, SET) shall also compile and run their tests headless on Linux. *Amended 2026-07-29: macOS (arm64) is added as an additional CI-covered GUI-app build target — see RQ-BLD-011/RQ-BLD-012 — without changing Windows' status as the primary target.*
- **RQ-BLD-003** — The code shall use C++20, compile warning-clean at high warning levels (/W4, -Wall -Wextra) with warnings-as-errors for project code.
- **RQ-BLD-004** — The C++ tree shall live in this repository under a dedicated top-level directory, leaving the .NET solution untouched and buildable during the whole migration.
- **RQ-BLD-005** — A single CMake invocation shall build libraries per layer (midi, framework, model, controller, settings), the application, and the test executables.
- **RQ-BLD-006** *(amended 2026-08-05, session ABT — architecture: ADR-ABT-002)* — All source files shall carry the **AGPL v3** header; JUCE shall be used under its **AGPL** option (no commercial JUCE license assumed).
  - *Amended 2026-08-05 (owner decision, session ABT) — relicensed from GPL v3 to AGPL v3.* The original wording ("GPL v3 header ... GPL option") was accurate for JUCE 6/7, which offered a GPLv3 open-source tier. **JUCE 8.0.9 — the pinned version (RQ-BLD-001) — offers AGPLv3, not GPLv3**, verified against the vendored tag's own `LICENSE.md` (finding surfaced by TASK-ABT-004/ADR-ABT-001 while writing the dependency-disclosure SBOM). GPLv3 §13 permits combining GPL and AGPL-licensed code, but the AGPL's network-source-disclosure obligation travels with the combination — so a project linking AGPL-licensed JUCE cannot correctly remain declared plain GPLv3. See ADR-ABT-002 for the full analysis and the (rejected) alternative of purchasing a commercial JUCE license to stay GPLv3. **Dependencies:** RQ-BLD-001, RQ-NFR-005; ADR-ABT-002.
  - **Acceptance (Gherkin):** *Given* the repository root, *When* `LICENSE` is read, *Then* it is the text of the GNU Affero General Public License, version 3. *Given* any source file carrying the project's licence header, *When* it is read, *Then* the header names the GNU Affero General Public License, not the GNU General Public License. *Given* `juce/CMakeLists.txt`, *When* its `SPDX-License-Identifier` line is read, *Then* it reads `AGPL-3.0-or-later`.
- **RQ-BLD-007** *(revised 2026-08-16, session BLD, owner decision during the canary/preprod trigger review)* — CI shall build and run the non-UI test suite on Linux (GitHub Actions), triggered manually (`workflow_dispatch`) rather than automatically on every push. *When this was decided, dropping the automatic trigger left Linux uncovered*: `linux-headless-release` was then the only Linux build in the pipeline. **TASK-BLD-006 has since closed that gap** — `linux-x64` is a full deployment platform (canary, preprod and prod), so Linux regressions are caught automatically again and this workflow is now only the headless, non-UI suite it always was.
- **RQ-BLD-010** *(SUPERSEDED 2026-08-16 by RQ-BLD-023, session BLD)* — its property is kept verbatim and its **form** is extended: `<os>-<application>-<build>` has no place for the architecture or the deployment stream that RQ-BLD-019 introduces, so the same rule now reads `<os>-<arch>-<config>-<stage>`. `linux-headless-release` is deliberately left outside the new scheme — it deploys nothing. — Each CI build workflow SHALL cover exactly one build configuration, and its **file name, workflow name and job name SHALL be identical**, formed as `<os>-<application>-<build>` — e.g. `linux-headless-release`, `windows-app-release`, `windows-app-debug`. *Rationale:* a status check in a pull request then names its own os/target/configuration without cross-referencing, and a workflow file can never hide a second, differently-configured job under an unrelated name (owner requirement, 2026-07-29). *Acceptance (Gherkin):* Given any workflow under `.github/workflows/`, When it is read, Then its `name:`, its single job key and its file stem are the same `<os>-<application>-<build>` string.
- **RQ-BLD-008** — The Windows (x64) GUI binary shall be produced with the MSVC toolchain. JUCE does not support MinGW (`juce_TargetPlatform.h` `#error`s on `__MINGW32__`), so cross-compiling the GUI app from Linux with MinGW-w64 is not viable; the amd64 `Xplorer.exe` is built by a native Windows CI job (`.github/workflows/windows-app-release.yml`) that also runs the unit suite and uploads the binary as an artifact.
- **RQ-BLD-009** *(SUPERSEDED 2026-08-16 by RQ-BLD-019, session BLD)* — its whole subject is "`main` publishes an alpha pre-release", and under the two-branch model `main` publishes **production** deployments while `dev` carries the pre-release stream. What it established survives in RQ-BLD-019/RQ-BLD-027: a preview build must be continuously available and must be impossible to mistake for production. — **EARS type: Event-driven.** WHEN a push lands on the `main` branch and the Windows CI build succeeds, the pipeline SHALL publish the resulting `Xplorer.exe` as a GitHub Release explicitly marked **pre-release**, distinctly tagged from production releases so it can never be mistaken for one (RQ-BLD-002/008 remain the production-build requirements, unaffected). The release notes SHALL be a concise summary of the changes (commit subjects) landed on `main` since the previous alpha release. *Rationale:* gives the owner/testers a continuously up-to-date, clearly-labelled preview build without polluting the production release stream. *Amended 2026-07-29: the alpha release is no longer Windows-only nor Release-only — RQ-BLD-013 generalises it to every platform and configuration CI builds, on a single shared release per commit, which also changes the tag derivation.* **Dependencies:** RQ-BLD-002, RQ-BLD-008, RQ-BLD-013.
  - **Acceptance (Gherkin):** *Given* a push to `main`, *When* the Windows build succeeds, *Then* a GitHub Release is created with `prerelease: true`, a tag distinct from production tags (e.g. `vX.Y.Z`), and `Xplorer.exe` attached. *Given* the same push, *When* the release is created, *Then* its notes list the commits landed since the previous alpha release, not the full project history. *Given* a production release is cut, *When* the Releases page is viewed, *Then* alpha releases are visually distinguishable (pre-release badge) and never the "Latest" one.
- **RQ-BLD-011** — **EARS type: Event-driven.** WHEN a push or pull request touches `juce/**`, CI SHALL build the JUCE GUI application for macOS (arm64) in Release configuration and upload the resulting `.app` bundle as a downloadable GitHub Actions artifact — mirroring RQ-BLD-008's Windows build. *Rationale:* the JUCE GUI app targets macOS as a real user platform, and a downloadable Release-config build lets the owner validate it without a local toolchain. *Amended 2026-07-29 (owner decision, same session, before merge): the original "CI artifact only, no GitHub Release" restriction is lifted — on `main` the bundle is additionally published to the shared alpha pre-release per RQ-BLD-013.* **Dependencies:** RQ-BLD-002, RQ-BLD-010, RQ-BLD-013, ADR-BLD-002.
  - **Acceptance (Gherkin):** *Given* a push or pull request touching `juce/**`, *When* `macos-app-release.yml` runs on `macos-latest` (arm64), *Then* the build succeeds in Release configuration and the produced `Xplorer.app` bundle is uploaded as a CI artifact. *Given* a run on `main`, *When* it completes, *Then* the bundle is additionally attached to that commit's shared alpha pre-release (RQ-BLD-013).
- **RQ-BLD-012** — **EARS type: Event-driven.** WHEN a push or pull request touches `juce/**`, CI SHALL also build the JUCE GUI application for macOS (arm64) in Debug configuration with tests enabled, running the full suite including the real-metrics combo-box fit check (`xpl_tests_app_juce`) against macOS's own font-rendering stack — extending the cross-platform fit guarantee of RQ-GUI-047/RQ-GUI-048/RQ-DSN-096 to a third platform, mirroring `windows-app-debug`. **Dependencies:** RQ-GUI-047, RQ-GUI-048, RQ-DSN-096, ADR-JUC-022, ADR-BLD-002.
  - **Acceptance (Gherkin):** *Given* a push or pull request touching `juce/**`, *When* `macos-app-debug.yml` runs on `macos-latest` (arm64), *Then* the build succeeds in Debug configuration with `XPL_BUILD_TESTS=ON` and `ctest` runs every suite, including `xpl_tests_app_juce`, to completion. *Given* a combo-box label that would overflow at the shipped size on macOS's real font metrics, *When* this workflow runs, *Then* `xpl_tests_app_juce` fails the build (not just logs).
- **RQ-BLD-013** *(SUPERSEDED 2026-08-16 by RQ-BLD-019/RQ-BLD-020/RQ-BLD-021, session BLD)* — the alpha stream on `main` is replaced (RQ-BLD-019), the tag derivation is replaced (RQ-BLD-020) and the asset shape is replaced (RQ-BLD-021, one archive carrying executable + `oberheim.syx` + SBOM instead of a bare binary). **Two of its properties are load-bearing and are carried forward unchanged**, because they are what makes several independent workflows converge on one release: the tag is derived from the **commit alone**, never from a per-workflow counter; and publication is **idempotent**, so whichever workflow arrives first creates the release and the others only add their asset. — **EARS type: Event-driven.** WHEN a push lands on `main` and a CI build workflow succeeds, that workflow SHALL attach its produced binary to **one single alpha pre-release shared by all build workflows for that commit**, covering every platform and configuration CI builds (Windows x64 Release/Debug, macOS arm64 Release/Debug), each asset named for its own os/architecture/configuration. The release tag SHALL be derived from the commit alone — never from a per-workflow counter such as `github.run_number`, which differs between workflows and would split one commit across several releases. Publication SHALL be idempotent, so that whichever workflow completes first creates the release and the others only add their asset. *Rationale:* a tester opens one page per commit and finds every build, instead of hunting across per-platform releases; Debug binaries are published because they are the ones that log their assertions when a tester reproduces a bug. **Dependencies:** RQ-BLD-009, RQ-BLD-011, RQ-BLD-012, ADR-BLD-002.
  - **Acceptance (Gherkin):** *Given* a push to `main` touching `juce/**`, *When* all four build workflows succeed, *Then* exactly one pre-release exists for that commit and it carries four distinctly-named assets. *Given* two build workflows finishing at the same moment, *When* both publish, *Then* one creates the release, the other adds its asset, and neither fails. *Given* a workflow whose release creation genuinely failed, *When* it attempts the upload, *Then* the run fails rather than silently reporting success.
  - *Amended 2026-08-06 (owner report, session GUI) — tag format readability.* The tag's per-commit component (originally `<commit-count>-<short-sha>`, DEC-BLD-010) is replaced by **HEAD's own committer timestamp, `YYYYMMDD-HHmmSS`, in UTC** (e.g. `alpha-20260806-230235`): the owner found the hex short-sha hard to read at a glance. The timestamp is read from the commit object itself, never from wall-clock "now" — the latter would differ across the four independently-run publishing workflows and break the "one shared tag" invariant this requirement itself states above; forcing UTC keeps the four runners (`windows-latest`, `macos-latest`) in agreement regardless of each one's own default timezone. **Traded off knowingly:** the short-sha's exact-commit traceability is gone from the tag itself (still recoverable from the release's own commit association), and two commits landing within the same UTC second would collide — judged negligible for this project's commit cadence. Per ADR-BLD-002 (DEC-BLD-011, supersedes DEC-BLD-010).
  - *Amended 2026-08-06 (owner report, session GUI, follow-up) — trigger coverage.* The DEC-BLD-011 change itself did not touch `juce/**`, so it did not auto-trigger any of the four workflows — surfacing a real gap: none of them watched the shared `.github/actions/alpha-prerelease` action they all depend on. Each workflow's `paths:` filter now also includes `.github/actions/alpha-prerelease/**`, so a future change to the shared publish logic is exercised by CI on every platform in the same push, rather than silently waiting for an unrelated `juce/**` change to carry it along. Per ADR-BLD-002 (DEC-BLD-012).
- **RQ-BLD-014** *(specified 2026-08-05, session ABT — architecture: ADR-ABT-001)* — **EARS type: Event-driven.** WHEN the JUCE application target is built, the build SHALL place a Software Bill of Materials in **SPDX 2.3 JSON** format, named **`xplorer.sbom.spdx.json`**, in the same directory as the produced executable, describing the third-party components the product depends on — so the running application can disclose them (RQ-GUI-057) by reading a build artifact rather than a hard-coded list.
  - **Format is fixed by its future producer.** SPDX (not CycloneDX) is required because it is the format GitHub's own dependency-graph export emits natively: a later CI step SHALL be able to replace the shipped file with GitHub's generated SBOM **without any application change**. The application's reader therefore depends on the SPDX schema only, never on this repository's particular file.
  - **Location is fixed by the consumer.** The file SHALL be a sibling of the executable, resolved at run time from the executable's own path — the same convention already used for the default patch `oberheim.syx` (RQ-GUI-008, DEC-JUC-100), so a copied or relocated install keeps working.
  - **Absence is not a build failure.** The application SHALL handle a missing or unusable SBOM as a normal, reported condition (RQ-GUI-057), so a developer build that skipped the copy still runs and still opens its dependency window.
  - *Rationale:* discharges the attribution obligations of the bundled components (RQ-BLD-006) with an artifact that is machine-generated at source, and decouples the disclosure content from the application's release cycle. **Priority:** Must. **Dependencies:** RQ-GUI-057, RQ-BLD-006, RQ-BLD-005; ADR-ABT-001.
  - **Acceptance (Gherkin):** *Given* a successful build of the application target, *When* the output directory is listed, *Then* `xplorer.sbom.spdx.json` sits beside the executable. *Given* that file, *When* it is parsed, *Then* it is valid JSON, declares an SPDX version, and its package list covers every third-party component bundled in the binary. *Given* a build tree where the file was deleted, *When* the application is launched and its dependency window opened, *Then* the application reports the absence and does not fail. *Given* GitHub's own dependency-graph SBOM for this repository, *When* it replaces the shipped file verbatim, *Then* the application reads it with no code change.

## Product Versioning

*Specified 2026-08-16, session BLD — architecture: ADR-BLD-003. Discharges the gap deliberately
deferred by RQ-GUI-025's note of 2026-08-05: the About box's version string was a hard-coded
literal matching neither the CMake project version nor any published release tag.*

> **Reworked 2026-08-16 (owner requirement, session BLD).** This section was drafted around a
> **semantic** version `MAJOR.MINOR.PATCH` **declared** in one file and validated against a pushed
> `vX.Y.Z` tag. The owner's delivery model replaces that with a version **derived from the commit**
> and a two-branch deployment flow (RQ-BLD-019..RQ-BLD-028). **RQ-BLD-015 and RQ-BLD-016 survive**
> — one source of truth, and an About box that reads what was built — but 015's mechanism changes
> from *single declaration* to *single derivation*: with a computed version there is no literal to
> be the single copy of. **RQ-BLD-017 and RQ-BLD-018 are superseded** by RQ-BLD-020 and RQ-BLD-028
> respectively. Nothing in this section was ever implemented, so the change costs no rework.

- **RQ-BLD-015** *(reworked 2026-08-16, session BLD — was "single declaration", now "single derivation")* — **Category:** Functional. **EARS type: Ubiquitous.** The product version SHALL be produced by **one derivation, in one place**, and every artifact that states a version — the CMake project, the GUI application target, the About dialog, the Windows executable's version resources, the macOS bundle's `Info.plist`, the generated SBOM's describing package, the deployment archive names and the release tag — SHALL take its value from that one derivation. No file in the repository SHALL contain a literal product version.
  - *Rationale:* the version is currently written out four times (`juce/CMakeLists.txt`, `juce/app/CMakeLists.txt`, `juce/app/src/MainComponent.cpp`, `juce/app/sbom/xplorer.sbom.spdx.json`) with nothing keeping them equal — the classic duplicated-literal defect the process forbids, here across four different languages. **Priority:** Must. **Dependencies:** RQ-BLD-001, RQ-BLD-005, RQ-BLD-014, RQ-BLD-020; ADR-BLD-003 (DEC-BLD-013, DEC-BLD-014, DEC-BLD-015).
  - **Acceptance (Gherkin):** *Given* the repository, *When* it is searched for the current version string, *Then* exactly one non-generated file declares it and every other occurrence is produced from that file at build time. *Given* the single declaration is changed to a new version, *When* the project is configured and built, *Then* the CMake project version, the application target version, the About dialog text and the shipped SBOM's describing package all report the new value with no other file edited.

- **RQ-BLD-016** — **Category:** Functional. **EARS type: Event-driven.** WHEN the user opens the About dialog, the application SHALL display the product name and version taken from the build's own compile-time definitions, never from a literal written in application source.
  - *Rationale:* closes the RQ-GUI-025 defect at its root — a source literal cannot be kept in step with the build, so the dialog must read what was actually built. **Priority:** Must. **Dependencies:** RQ-BLD-015, RQ-GUI-025; ADR-BLD-003 (DEC-BLD-015).
  - **Acceptance (Gherkin):** *Given* the application sources, *When* they are searched for a literal product version, *Then* there is no match. *Given* a build whose declared version is `X.Y.Z`, *When* the About dialog is opened, *Then* its version row reads the product name followed by `X.Y.Z`. *Given* the declared version is changed and the application rebuilt, *When* the About dialog is opened, *Then* it reports the new version with no source edit.

- **RQ-BLD-017** *(SUPERSEDED 2026-08-16 by RQ-BLD-020 — never implemented)* — the alpha stream it tags no longer exists: `main` publishes production deployments and `dev` publishes pre-releases (RQ-BLD-019), and the version is derived from the commit rather than from a declared semantic triple (RQ-BLD-020). **Its one durable idea is carried forward**: a workflow may never tag a binary with a version the binary does not itself report — RQ-BLD-020 gets that for free, since both come from the same derivation. Kept here as the record of what was considered. — **Category:** Functional. **EARS type: Event-driven.** WHEN a build workflow publishes into the shared alpha pre-release (RQ-BLD-013), the release tag SHALL carry the semantic product version of RQ-BLD-015 alongside the commit timestamp, formed as `v<MAJOR>.<MINOR>.<PATCH>-alpha-<YYYYMMDD-HHmmSS>`.
  - **The invariants of RQ-BLD-013 are preserved, not relaxed.** The tag SHALL still be derived from the commit alone, so all four independently-run publishing workflows compute the identical string; and publication SHALL remain idempotent. The version component is read from the same single declaration the build uses, so a workflow can never tag a binary with a version the binary does not itself report.
  - *Rationale:* an alpha asset currently states no version at all, so a tester reporting a bug cannot say which product version they ran; and the tag stream carries no ordering beyond the timestamp. **Priority:** Must. **Dependencies:** RQ-BLD-013, RQ-BLD-015, RQ-BLD-018; ADR-BLD-003 (DEC-BLD-016, supersedes DEC-BLD-011's format).
  - **Acceptance (Gherkin):** *Given* a push to `main` with declared version `X.Y.Z`, *When* any build workflow publishes, *Then* the tag reads `vX.Y.Z-alpha-YYYYMMDD-HHmmSS` using HEAD's own committer time in UTC. *Given* all four build workflows for one commit, *When* each computes its tag independently, *Then* all four compute the identical string and exactly one release exists for that commit. *Given* a production tag `vX.Y.Z` (RQ-BLD-018), *When* the alpha tag for the same version is read, *Then* the two are distinct strings and the alpha one is unambiguously marked pre-release.

- **RQ-BLD-018** *(SUPERSEDED 2026-08-16 by RQ-BLD-028 — never implemented)* — the shape survives (a pushed tag triggers the production build, which is not a pre-release and takes the "Latest" badge) but its **tag-versus-declaration check is impossible under RQ-BLD-020**: a version derived from the commit cannot be typed into a tag before that commit is built. RQ-BLD-028 resolves it by having the tag *computed and pushed by CI* rather than hand-written, which makes the check unnecessary instead of merely automatic. Kept here as the record. — **Category:** Functional. **EARS type: Event-driven.** WHEN a tag matching `v<MAJOR>.<MINOR>.<PATCH>` **with no suffix** is pushed, CI SHALL build every platform and configuration it covers and publish **one** GitHub Release for that tag which is **not** a pre-release and **is** marked as the repository's latest release, carrying every built binary as a distinctly-named asset.
  - **The tag SHALL agree with the build.** IF the version encoded in the pushed tag is not equal to the single declaration of RQ-BLD-015, THEN the workflow SHALL fail without publishing anything, and its failure message SHALL name both values. *(EARS type: Unwanted-behavior.)* This is what makes the production tag a statement about the product rather than about the tagger.
  - **The alpha stream is unaffected.** Alpha pre-releases (RQ-BLD-009/RQ-BLD-013/RQ-BLD-017) continue to publish on `main` exactly as before, and SHALL never take GitHub's "Latest" badge from a production release.
  - *Rationale:* the project has published only `alpha-*` pre-releases since inception and has no way to cut a release a user could be pointed at; RQ-BLD-009 already presumes a production stream (`vX.Y.Z`) that has never existed. **Priority:** Must. **Dependencies:** RQ-BLD-013, RQ-BLD-015, RQ-BLD-010; ADR-BLD-003 (DEC-BLD-017, DEC-BLD-018).
  - **Acceptance (Gherkin):** *Given* the declared version is `X.Y.Z`, *When* tag `vX.Y.Z` is pushed, *Then* CI builds every covered platform/configuration and publishes exactly one release for that tag with `prerelease: false` and `make_latest: true`, carrying every built binary. *Given* the declared version is `X.Y.Z`, *When* tag `vA.B.C` with `A.B.C ≠ X.Y.Z` is pushed, *Then* the workflow fails, names both versions in its error, and no release is created. *Given* a production release exists, *When* a later alpha pre-release publishes from `main`, *Then* the production release keeps the "Latest" badge. *Given* a production release page, *When* it is viewed, *Then* it carries no pre-release badge and its assets name their own os/architecture/configuration.

## Delivery Model — two long-lived branches, three deployment streams

*Specified 2026-08-16, session BLD — architecture: ADR-BLD-003 (branching, versioning, release
streams) and ADR-BLD-004 (per-platform build and packaging). Owner requirement.*

**Vocabulary, fixed by the owner and used consistently below.** A **deployment** is a GitHub
Release. It is never a synonym for a *release build* — that phrase is reserved for the CMake
configuration (`Release` vs `Debug`). The two words were colliding in RQ-BLD-009/011/013 and the
distinction is what this section is written against.

- **RQ-BLD-019** — **Category:** Functional. **EARS type: Ubiquitous.** The repository SHALL carry **two long-lived branches** and feature branches, and each SHALL have exactly one deployment behaviour:
  - **`main`** — production. Deployments from `main` SHALL be GitHub Releases that are **not** pre-releases and that take the repository's **Latest** badge. `main` SHALL be built in **Release configuration only**.
  - **`dev`** — integration / pre-production, and the repository's **default branch**. Deployments from `dev` SHALL be GitHub Releases marked **pre-release**, carrying a note stating plainly that they are not production deployments. `dev` SHALL be built in **both Debug and Release** configurations.
  - **`feature/*`** — canary. These SHALL produce **no deployment at all**, in neither stream; their binaries SHALL remain GitHub Actions artifacts of their own run. They SHALL be built in both Debug and Release.
  - **Protection.** `main` SHALL be protected explicitly. *This is not automatic:* GitHub protects the default branch only through a rule, and `dev` is taking that role — leaving `main` to inherit protection would leave it with none.
  - *Rationale:* owner requirement, 2026-08-16 — the single-branch model gives no place to integrate and validate a change before it reaches the stream users are pointed at. **Priority:** Must. **Dependencies:** RQ-BLD-020, RQ-BLD-028; ADR-BLD-003 (DEC-BLD-013). **Supersedes:** RQ-BLD-009 and RQ-BLD-013, whose whole subject is "`main` publishes an alpha pre-release".
  - **Acceptance (Gherkin):** *Given* the repository settings, *When* the default branch is read, *Then* it is `dev`. *Given* a push to `dev`, *When* its workflows complete, *Then* exactly one GitHub Release exists for that commit, marked pre-release, and it does not hold the Latest badge. *Given* a production deployment from `main`, *When* the Releases page is viewed, *Then* it carries no pre-release badge and holds the Latest badge. *Given* a push to any `feature/*` branch, *When* its workflows complete, *Then* no release and no tag were created and the binaries are downloadable only from the run's artifacts. *Given* a pull request that targets `dev`, *When* its verification workflows complete, *Then* they build and run the tests against the merge result but publish no release — only the eventual push that lands the merge on `dev` publishes (ADR-BLD-003, DEC-BLD-024). *Given* the branch protection rules, *When* they are read, *Then* `main` is covered by one.

- **RQ-BLD-020** — **Category:** Functional. **EARS type: Ubiquitous.** The product version SHALL be **derived from the commit being built**, as `YYYY.MM.DD-HHMM` taken from that commit's own committer timestamp **in UTC**, with a stage suffix appended for non-production streams. The derivation SHALL produce **three forms**, and each consumer SHALL take the form it can carry:

  | form | example | consumers | why this form |
  |---|---|---|---|
  | numeric | `2026.8.19.1740` | CMake `project(VERSION)`, `juce_add_gui_app(VERSION)`, Windows `FILEVERSION`/`PRODUCTVERSION`, `CFBundleVersion` | four integers, no zero-padding, no suffix |
  | display | `2026.08.19-1740` | release tag, release title, deployment archive names | human-readable, zero-padded |
  | full | `2026.08.19-1740-preprod` | About dialog, Windows `ProductVersion` **string**, `CFBundleShortVersionString`, SBOM describing package | carries the stage |

  - **Stage suffix.** `refs/heads/main` **or any tag** → none; `refs/heads/dev` → `-preprod`; any other ref → `-canary`.
    - *Corrected 2026-08-16, during TASK-BLD-002, before any workflow existed.* This rule first read "`main` → none; `dev` → `-preprod`; **any other ref** → `-canary`" — and a production build never runs on `refs/heads/main`. RQ-BLD-028 has it triggered by the **tag** `cut-deployment` pushes, so its ref is `refs/tags/…` and it would have fallen through to `-canary`: **every production binary would have shipped stamped as a canary build**, in its About box, its `ProductVersion` string and its SBOM alike. Treating a tag as production is sound rather than expedient, because tags are minted by `cut-deployment` on `main` alone (DEC-BLD-017) — a tag *is* the production stream. The case is pinned by a test.
    - *Falling out of that:* a build triggered from the tag derives the same `display` form as the tag's own name, since both come from the same commit. A production workflow can therefore assert `github.ref_name == display` for free, and catch a hand-pushed tag that `cut-deployment` did not create.
  - **Derived, never assigned.** The version SHALL be a **pure function of the commit**: no counter, no `github.run_number`, no repository variable, no wall-clock "now". *This is a load-bearing property, not a preference* — the six workflows that build one `dev` commit run independently and must compute the identical string without communicating, which is the same invariant RQ-BLD-013 already depends on. It also makes a re-run of a failed workflow produce the same version rather than a new one.
  - **Why not the owner's original "Nth build of the day, across all branches".** That is a mutable counter shared by every branch, and it cannot be satisfied without shared state: GitHub offers no atomic counter, the default `GITHUB_TOKEN` cannot write repository variables, canary builds consume numbers while publishing nothing (so the count is not reconstructible from releases), and a workflow re-run would burn a fresh number. `HHMM` keeps the shape the owner asked for, is globally unique without any state, and orders identically. Owner decision, 2026-08-16, after that trade was put to them.
  - **The numeric form is constrained by Windows, not chosen.** `FILEVERSION` is four **16-bit** fields (0–65535). `2026.8.19.1740` fits; the unpunctuated `20260819` the owner first wrote does not, and the stage suffix cannot appear there at all — hence three forms rather than one.
  - *Rationale:* owner requirement — a deployment must state a unique version everywhere it can, so a bug report names an artifact unambiguously. **Priority:** Must. **Dependencies:** RQ-BLD-015, RQ-BLD-016, RQ-BLD-019; ADR-BLD-003 (DEC-BLD-014, DEC-BLD-015). **Supersedes:** RQ-BLD-017.
  - **Acceptance (Gherkin):** *Given* a commit whose UTC committer time is 2026-08-19 17:40, *When* the version is derived on `dev`, *Then* the three forms are `2026.8.19.1740`, `2026.08.19-1740` and `2026.08.19-1740-preprod`. *Given* the same commit built by all six `dev` workflows, *When* each derives the version independently, *Then* all six produce identical strings. *Given* a workflow that failed and is re-run, *When* it derives the version again, *Then* it is unchanged. *Given* a build on a `feature/*` branch, *When* the About dialog is opened, *Then* it reads `…-canary`. *Given* the derivation, *When* it is searched for `run_number`, a repository variable or a wall-clock date, *Then* there is no match.

- **RQ-BLD-021** — **Category:** Functional. **EARS type: Event-driven.** WHEN a deployment is published, each platform/configuration it covers SHALL be carried by **one archive** containing exactly three things: the application executable (or bundle), the default patch **`oberheim.syx`**, and the **generated SBOM**. The archive name SHALL state the version, the operating system, the architecture and the build configuration.
  - *Rationale:* owner requirement. `oberheim.syx` is what File > New loads (RQ-GUI-008); a deployment without it produces an application that cannot create a patch. Today no release asset carries it at all — the four workflows upload a bare executable. **Priority:** Must. **Dependencies:** RQ-GUI-008, RQ-BLD-022, RQ-GUI-057; ADR-BLD-004.
  - **Acceptance (Gherkin):** *Given* any published deployment, *When* one of its assets is downloaded and expanded, *Then* it contains the executable, `oberheim.syx` and `xplorer.sbom.spdx.json`, and nothing else is required for the application to start and create a patch. *Given* a deployment's asset list, *When* the names are read, *Then* each states its version, os, architecture and configuration and no two collide.

- **RQ-BLD-022** — **Category:** Functional. **EARS type: Event-driven.** WHEN a deployment is built, its SBOM SHALL be **generated by that build** rather than copied from a file committed to the repository, and its describing package SHALL carry the **full** version form of RQ-BLD-020.
  - **RQ-BLD-014 is refined, not replaced.** The format (SPDX 2.3 JSON), the file name, the sibling-of-the-executable location and the "absence is not a build failure" rule all stand unchanged; only the *producer* changes, from a committed artefact to a build step. ADR-ABT-001 (DEC-ABT-002) anticipated exactly this move.
  - **The generator must see what the build actually links.** *Noted as a constraint, not a choice of tool:* JUCE arrives through CMake `FetchContent`, which GitHub's dependency graph does not observe — so GitHub's own SPDX export would describe a project that does not include its largest dependency. Whatever generator is chosen SHALL cover the components actually linked into the binary.
  - *Rationale:* owner requirement; and a committed SBOM cannot state a version that is only known at build time (RQ-BLD-020). **Priority:** Must. **Dependencies:** RQ-BLD-014, RQ-BLD-020, RQ-GUI-057; ADR-BLD-004, ADR-ABT-001.
  - **Acceptance (Gherkin):** *Given* a deployment build, *When* the SBOM is opened, *Then* its describing package version equals the built binary's full version. *Given* the repository, *When* it is searched for a committed SBOM used as a build input, *Then* there is none. *Given* the generated SBOM, *When* its package list is read, *Then* JUCE appears in it. *Given* the application built from that deployment, *When* its dependency window is opened, *Then* it reads the generated file with no code change (RQ-GUI-057 unaffected).

- **RQ-BLD-023** — **Category:** Functional. **EARS type: Ubiquitous.** Each deployment workflow SHALL cover exactly one operating system, architecture, build configuration and stream, and its **file name, workflow name and job name SHALL be identical**, formed as `<os>-<arch>-<config>-<stage>`:

  ```
  windows-x64-release-prod      windows-x64-{debug,release}-preprod   windows-x64-{debug,release}-canary
  macos-arm64-release-prod      macos-arm64-{debug,release}-preprod   macos-arm64-{debug,release}-canary
  linux-x64-release-prod        linux-x64-{debug,release}-preprod     linux-x64-{debug,release}-canary
  ```

  - **The shared logic SHALL live in composite actions**, not be copied into one file per combination. *Reusable workflows (`workflow_call`) are excluded by this requirement's own naming rule*: a called workflow's status check is reported as `<caller> / <called job>`, which is no longer the single string a reviewer can read. Composite actions keep the check name equal to the job name.
  - **`linux-headless-release` stays outside this scheme.** It builds no application and deploys nothing — it is the non-UI test job of RQ-BLD-007. Renaming it to fit a deployment nomenclature would state something false about it.
  - *Rationale:* extends RQ-BLD-010's property (a status check names its own os/target/configuration without cross-referencing) to a matrix that now also has an architecture and a stream. **Priority:** Must. **Dependencies:** RQ-BLD-019; ADR-BLD-003 (DEC-BLD-016). **Supersedes:** RQ-BLD-010, whose `<os>-<application>-<build>` form has no place for either.
  - **Acceptance (Gherkin):** *Given* any deployment workflow, *When* it is read, *Then* its `name:`, its single job key and its file stem are the same `<os>-<arch>-<config>-<stage>` string. *Given* the fifteen deployment workflows (`windows-x64`, `macos-arm64`, `linux-x64`), *When* their build steps are compared, *Then* the shared logic appears once, in composite actions under `.github/actions/`. *Given* a pull request, *When* its checks are listed, *Then* each name states its own os, architecture, configuration and stream. *Given* `linux-headless-release`, *When* it is read, *Then* it keeps its name and carries a note saying why it is outside the scheme.

- **RQ-BLD-024** — **Category:** Functional. **EARS type: Unwanted-behavior.** IF a Windows Debug binary is published in a deployment, THEN it SHALL be linked against the **static** debug C runtime, so that it starts on a machine with no Visual Studio installed.
  - *Rationale:* the dynamic debug CRT (`MSVCP140D.dll`, `VCRUNTIME140D.dll`) is **not redistributable** and exists only where Visual Studio is installed. The project sets no runtime-library policy today, so it takes the dynamic default — and `windows-app-debug.yml` already publishes `Xplorer-windows-x64-debug.exe`, meaning the defect is live now and merely unreported. Under RQ-BLD-019 `dev` publishes Debug binaries deliberately, so this stops being incidental. **Priority:** Must. **Dependencies:** RQ-BLD-008, RQ-BLD-019; ADR-BLD-004 (DEC-BLD-020).
  - **The policy SHALL be set repository-wide, before JUCE is fetched.** *Not a style point:* `MSVC_RUNTIME_LIBRARY` is a per-target property, so setting it on the application alone while JUCE keeps the dynamic runtime makes the link fail with `LNK2038`. Every target in the build must agree.
  - **Acceptance (Gherkin):** *Given* a published Windows Debug binary, *When* it is launched on a machine without Visual Studio, *Then* it starts. *Given* the built executable, *When* its imports are listed, *Then* no `*D.dll` C-runtime module appears. *Given* the CMake tree, *When* the runtime-library policy is read, *Then* it is set once, before JUCE is made available, so application and dependency agree.

- **RQ-BLD-025** — **Category:** Functional. **EARS type: Event-driven.** WHEN a deployment covers Linux, CI SHALL build the **JUCE GUI application for `linux-x64`** and package it as an **AppImage**.
  - **This build does not exist today.** CI covers only `linux-headless-release`, which builds the non-UI layers. The GUI build additionally needs X11, Xrandr, Xinerama, Xcursor, Xcomposite, Xext, FreeType, Fontconfig, ALSA and GL development packages. It does **not** need libcurl or WebKit: `JUCE_USE_CURL=0` and `JUCE_WEB_BROWSER=0` are already set.
  - **The runner SHALL be the oldest supported Ubuntu image, not `ubuntu-latest`.** A binary linked against a newer glibc will not start on an older distribution, and the failure appears only on the user's machine.
  - **AppImage, chosen for the user.** Owner decision, 2026-08-16: "*ce doit être simple pour l'utilisateur — les geeks compileront les sources de toute façon*". A bare ELF would need the same libraries present and correctly versioned on the target.
  - *Rationale:* Linux is a supported 64-bit platform for this application and has never had a GUI build. **Priority:** Must. **Dependencies:** RQ-BLD-002, RQ-BLD-021, RQ-BLD-026; ADR-BLD-004 (DEC-BLD-021).
  - **Acceptance (Gherkin):** *Given* a deployment build for Linux, *When* it completes, *Then* an AppImage is produced and included in the deployment archive with `oberheim.syx` and the SBOM. *Given* that AppImage on a supported distribution, *When* it is made executable and run, *Then* the application window opens. *Given* the Linux workflows, *When* their runner image is read, *Then* it is pinned, not `ubuntu-latest`.

- **RQ-BLD-026** — **Category:** Functional. **EARS type: Ubiquitous.** The application SHALL carry an **application icon** on every platform: the Windows executable and its windows, the macOS bundle, and the Linux AppImage and its desktop entry.
  - **The icon already exists in this repository** and SHALL be reused rather than redrawn: `xdata/IconeXplorer/Hazard_256.png` and its smaller siblings. JUCE generates the Windows `.ico` and the macOS `.icns` from these PNGs itself, so `Xplorer.ico` is not a build input and remains the archived original.
  - **This is a prerequisite of RQ-BLD-025, not an embellishment.** An AppImage requires a `.desktop` entry and an icon; the application currently declares neither `ICON_BIG` nor `ICON_SMALL` and has no icon asset at all — which is also why its executable and its main window show the platform's generic icon.
  - **ADR-GUI-001's "no binary asset" rule does not apply here.** That decision governs *control-surface* icons, painted every frame by `juce::Path`. An application icon is OS chrome consumed by the shell, the same category as the `about.jpg` and `menu_*.png` already kept verbatim from the reference.
  - *Rationale:* owner instruction, 2026-08-16, on being asked how the AppImage should be iconified. **Priority:** Must. **Dependencies:** RQ-BLD-025, RQ-GUI-070; ADR-BLD-004 (DEC-BLD-023), ADR-GUI-001 (referenced, not amended).
  - **Acceptance (Gherkin):** *Given* the built Windows executable, *When* it is viewed in Explorer, *Then* it shows the Xplorer icon and not the generic one. *Given* the macOS bundle, *When* it is viewed in Finder, *Then* it shows the same icon. *Given* the AppImage, *When* it is placed in a desktop environment, *Then* its entry shows the same icon. *Given* the repository, *When* it is searched for a second copy of the icon artwork, *Then* there is none.

- **RQ-BLD-027** — **Category:** Functional. **EARS type: Event-driven.** WHEN a deployment is published — from `main` or from `dev` alike — its release notes SHALL carry a **concise first-launch notice covering Windows, macOS and Linux**, stating that the binaries are unsigned and giving the one action each operating system requires of the user.
  - **The binaries will not be signed.** Owner decision, 2026-08-16: an Apple Developer ID costs 99 USD/year and is the only way to satisfy Gatekeeper; the owner declines to fund it for an AGPL project. Windows code-signing certificates are a comparable recurring cost with the same conclusion. The notice is the accepted mitigation, recorded rather than left to the user to discover.
  - **The notice SHALL be generated with the deployment**, from one source shared by both streams, not written by hand per release.
  - *Rationale:* without it every platform silently blocks the download — SmartScreen on Windows, Gatekeeper quarantine on macOS, and a non-executable file on Linux — and each looks to a user like a broken build. **Priority:** Must. **Dependencies:** RQ-BLD-019, RQ-BLD-021, RQ-BLD-025; ADR-BLD-004 (DEC-BLD-022).
  - **Acceptance (Gherkin):** *Given* any published deployment, *When* its notes are read, *Then* they state that the binaries are unsigned and give one instruction each for Windows, macOS and Linux. *Given* the macOS instruction, *When* it is read, *Then* it names the System Settings route and does not tell the user to right-click → Open, which macOS 15 removed. *Given* the Linux instruction, *When* it is read, *Then* it covers both the executable bit and the FUSE-less fallback. *Given* two deployments from different streams, *When* their notices are compared, *Then* they are identical and generated from one source.

- **RQ-BLD-028** — **Category:** Functional. **EARS type: Event-driven.** WHEN a production deployment is wanted, it SHALL be cut by an **explicit manual action on `main`** which derives the version (RQ-BLD-020), pushes it as a tag, and thereby triggers the three production workflows (`windows-x64`, `macos-arm64`, `linux-x64`); a push to `main` on its own SHALL NOT publish a deployment.
  - **The version SHALL NOT be typed by a human.** *This is what makes a tag trigger possible at all:* the version is a function of the commit, so it cannot be known before the commit exists, and a hand-written tag could disagree with what the binaries report. Having CI compute and push it removes the disagreement instead of checking for it — which is why RQ-BLD-018's tag-versus-declaration check is superseded rather than carried over.
  - **The production notes SHALL name the pre-production build being promoted.** The merge into `main` is a new commit, so a production deployment carries a different version from the `dev` pre-release that was actually tested. That is inherent to rebuilding on `main` (which RQ-BLD-019 requires) and is accepted; naming the promoted build in the notes is what keeps the chain readable.
  - *Rationale:* owner choice, 2026-08-16, between "every push to `main` deploys" and a human gate. **Priority:** Must. **Dependencies:** RQ-BLD-019, RQ-BLD-020, RQ-BLD-023; ADR-BLD-003 (DEC-BLD-017). **Supersedes:** RQ-BLD-018.
  - **Acceptance (Gherkin):** *Given* a push to `main` with no tag, *When* its workflows complete, *Then* no deployment was published. *Given* the cut action run on `main`, *When* it completes, *Then* a tag equal to the display version exists and every production workflow has run. *Given* the resulting release, *When* it is viewed, *Then* it is not a pre-release, holds the Latest badge, and its notes name the `dev` pre-release it promotes. *Given* the cut action, *When* its inputs are read, *Then* none of them is a version string.
